# macOS 日本語入力プログラムを実機で調べる方法（提案）

[macos.md](macos.md) は Apple の資料から作ったので、「資料に無い」「出典で食い違う」が多く残っている。
これを Mac の実機で確かめる方法を調べ、小さな試作で動くことを確かめた。Windows の [tools/keyprobe](../../tools/keyprobe/README.md) に当たるものを Mac 用に作る提案である。

- 試作した環境: MacBook Air (M1)、macOS 27.2.1、内蔵キーボードは US 配列、入力ソースは「日本語 - ローマ字入力」（ひらがなだけ有効）と ABC。2026-11-22。
- 「確かめた」と書いたものは、この環境で試作を動かして見た結果。「未検証」と書いたものは動かしていない。

---

## 1. 結論

| 項目 | 内容 |
|---|---|
| 方法 | 試験用の小さなアプリ（Swift、1 ファイル）を作る。窓の中のビューが `NSTextInputClient` を実装し、日本語入力プログラムからの呼び出しをすべて JSON の行で記録する。キーは、同じアプリの中で `NSEvent` を合成して `NSApp.sendEvent` に渡す |
| AI だけでできる範囲 | 入力中・変換中・候補選択中のキーの大半。文字列、文節の区切り、注目文節、確定した文字、IME が食べなかったキー、英数/かなキーでの入力ソースの切り替えまで採れる（確かめた） |
| 要る許可 | 上の範囲は**許可が要らない**（アクセシビリティも入力監視も不要）。候補ウインドウを画像で見るときだけ「画面収録」の許可が 1 回要る（許可済み） |
| 人の手が要るもの | 許可のダイアログ（初回）、設定画面でしか変えられない設定の切り替え、システムが先に取るキー（Control＋Space、Caps Lock、地球儀キー）、押し続けと本物のキーボードとの差の確認。§6 |
| Windows 版より楽な点 | キーが試験アプリの外に出ないので、別の窓にキーが行く事故が起きない。前面の窓の確認（`lib.guard`）に当たるものは、プロセス内の方式では要らない |

## 2. Windows の道具との対応

| Windows（tools/keyprobe） | Mac での対応 | 状況 |
|---|---|---|
| `SendInput` でキーを送る | プロセス内で `CGEvent` → `NSEvent(cgEvent:)` → `NSApp.sendEvent` | 確かめた。許可不要 |
| `target_tsf.py` / `target_imm.py`（届いたキーと文字を記録する窓） | `NSTextInputClient` を実装したビュー。`setMarkedText`・`insertText`・`doCommand(by:)` を記録 | 確かめた |
| 変換中の文字列と属性（IMM の `GCS_COMPATTR`） | `setMarkedText` の属性付き文字列。`NSMarkedClauseSegment`（文節の番号）、`NSUnderline`（2 ＝ 太い ＝ 注目文節、1 ＝ 細い）、選択範囲 | 確かめた |
| 「アプリに届いた down」（IME が食べなかったキー） | `doCommand(by:)` に来るセレクタ（`insertNewline:`、`moveLeft:`、`cancelOperation:` など）と、`inputContext.handleEvent` の戻り値 | 確かめた。下の注意 |
| IME の開閉と入力モード（`status`） | `NSTextInputContext.selectedKeyboardInputSource` と `keyboardSelectionDidChangeNotification`。入力モードは入力ソース ID で区別される | 確かめた（ABC ↔ ひらがな） |
| Alt+\` で MS-IME をオンにする | `inputContext.selectedKeyboardInputSource = "com.apple.inputmethod.Kotoeri.RomajiTyping.Japanese"` | 確かめた |
| `msime_tsf_seq.py` の画面の撮影（候補ウインドウ） | `screencapture -x -o -l <窓番号>`。候補ウインドウは試験アプリ自身の窓として出るので、窓番号は `NSApp.windows` から取れる | 確かめた。画面収録の許可が要る |
| `msime_tsf_table.py`（状態 × キーの表） | 同じ作りで書ける（状態を作る → キー 1 つ → 記録 → Esc で片付け → 残った文字を見る） | 未実装 |
| 確認用の TIP（TSF が TIP をどう呼ぶか） | 対応するものは要らない。Mac 向けの IME を作るわけではないので、InputMethodKit の呼ばれ方は調べなくてよい | — |
| `manual-start` / `manual-report`（本物のキーボードで押す） | 同じ試験アプリを「記録だけ」のモードで開き、人が押す | 未実装 |

「食べなかったキー」の注意: `handleEvent` の戻り値は、IME が食べなくてもテキスト入力の仕組みがキーをコマンドに変えれば `true` になる（未入力で Return を押すと `handled=true` で `insertNewline:` が来る）。食べたかどうかは、`doCommand` や素通しの `insertText` が来たかで判断する。

## 3. 仕組み

### 3.1 キーを入れる 4 つの方式

| 方式 | やり方 | 許可 | 結果 |
|---|---|---|---|
| A. プロセス内（アプリ経由） | `CGEvent(keyboardEventSource:virtualKey:keyDown:)` で作り、`NSEvent(cgEvent:)` にして `NSApp.sendEvent` に渡す | 不要 | **採用**。入力・変換・候補・英数/かなキーまで動いた |
| B. プロセス内（ビューへ直接） | 同じイベントをビューの `keyDown(with:)` に直接渡す | 不要 | 入力と変換は動くが、英数/かなキーと Control＋Shift＋J などのモード切替が効かない（`handled=true` なのに入力ソースが変わらない）。使わない |
| C. 自分のプロセスへ送る | `CGEvent.postToPid(getpid())` | アクセシビリティ | 許可が無いと黙って捨てられる（確かめた）。許可ありは未検証 |
| D. システム全体へ送る | `CGEvent.post(tap: .cghidEventTap)` | アクセシビリティ | 未検証。本物のキーと同じ道を通るので、システムが先に取るキー（§5）を調べるならこれ。Windows 版と同じく、前面が試験アプリのときだけ送る確認が必須 |

- 矢印キーには `.maskNumericPad` と `.maskSecondaryFn`、ファンクションキーと Home/End/Page Up/Down には `.maskSecondaryFn` のフラグを付ける（本物のイベントに合わせる）。
- アクセシビリティの許可は、試験アプリを起動した親（ターミナルや VS Code）に付く。試作時点では未許可（`AXIsProcessTrusted()` も `CGPreflightPostEventAccess()` も false）。

### 3.2 記録するもの

1 つのキーごとに次を 1 行ずつ書く（試作の出力そのまま）。

```
{"ev":"press","key":"{Space}"}
{"ev":"setMarkedText","s":"今日は雨です","segs":[{"at":0,"len":3,"NSMarkedClauseSegment":0,"NSUnderline":2,"s":"今日は"},{"at":3,"len":3,"NSMarkedClauseSegment":1,"NSUnderline":1,"s":"雨です"}],"sel":[0,3]}
{"ev":"keyDown","code":49,"chars":" ","handled":true}
{"ev":"after","text":"","marked":"今日は雨です","sel":[0,3],"source":"com.apple.inputmethod.Kotoeri.RomajiTyping.Japanese"}
```

| 行 | 中身 |
|---|---|
| `setMarkedText` | 変換中の文字列、文節ごとの属性、選択範囲（入力中はカーソルの位置、変換中は注目文節の範囲） |
| `insertText` | 確定した文字、または IME を素通りした文字 |
| `doCommand` | IME が食べずにアプリへ渡したキーのコマンド |
| `source` | 入力ソースが変わった（通知） |
| `after` | キーのあと 0.45 秒待ってからの、確定済みの文字・変換中の文字・入力ソース・開いている候補ウインドウ |

### 3.3 候補ウインドウ

- 候補ウインドウ（変換候補も推測候補も）は、別プロセスの窓ではなく、**試験アプリ自身の窓**（クラス `NSPanel.ViewBridge.rendezvous`、中身は `NSRemoteView`）として出る。開いているか・大きさ・位置は `NSApp.windows` で分かる（許可不要）。
- 中身は別プロセスが描くので、アプリの中からは読めない。
  - `cacheDisplay` で撮ると中身の無い画像になる。
  - アプリ内のアクセシビリティの木をたどると `NSAccessibilityRemoteUIElement` に当たり、そこから先は取れない。
- `screencapture -x -o -l <windowNumber> out.png` で、その窓だけを撮れる（画面収録の許可が要る）。撮った画像は AI が読める。番号、注目している候補、下のタブ（標準・読み・部首・名前・記号）、辞書の印まで写る。
- 画像に頼らずに分かること: Space を押すたびに `setMarkedText` の注目文節の文字が変わるので、候補の順序は文字として採れる。ページ送りのキーは、何件飛んだかで分かる。

### 3.4 状態を作る・片付ける

| 状態 | 作り方 |
|---|---|
| 未入力（ひらがな） | 入力ソースをひらがなにして、何も打たない |
| 入力中 | `kyouhaamedesu` |
| 入力中（途中にカーソル） | 入力中 → `{Left}` |
| 変換中（文節が複数） | 入力中 → `{Space}` |
| 候補選択中 | 変換中 → `{Space}`（候補ウインドウが開く） |
| 推測候補が出ている | 2 文字ほど打つ（`he` で開いた） |
| ライブ変換の途中 | 設定でライブ変換をオンにして入力（§6） |
| 英字（ABC） | 入力ソースを ABC にする |

片付けは Esc を数回（候補選択中 → 入力中 → 空、の順に戻る）。確定してしまった文字は試験アプリが自分で持っているので、変数を空にすれば済む（Windows 版の Ctrl+A → Delete は要らない）。
表の 1 件ごとに、入力ソースがひらがなであること、変換中の文字が無いことを確かめ、違えば窓を作り直す。

## 4. 試作で確かめたこと

| 確かめたこと | 結果 |
|---|---|
| ローマ字の入力 | `k` `y` `o` `u` で `k` → `ky` → `きょ` → `きょう`。途中のローマ字も変換中の文字列に入る |
| Space で変換 | 文節に分かれ、先頭が注目文節（太い下線、`sel` がその範囲） |
| Shift＋← | 注目文節が縮み、文節が 2 → 3 に増えた |
| Return | 変換中は `insertText` で全体が確定。未入力では `insertNewline:` がアプリへ |
| 未入力の ←、Control＋A | `moveLeft:`、`moveToBeginningOfParagraph:` がアプリへ（IME は食べない） |
| Control＋J / K / L / ; と F7 | 入力中に ひらがな / カタカナ / 全角英字 / 半角英字 に変わり、変換中の文字列のまま留まる（確定しない） |
| Esc | 候補選択中 → 読みに戻る → もう 1 回で空になる → さらに押すと `cancelOperation:` がアプリへ |
| 候補選択中の ↓、Control＋N / P、Tab、数字、Shift＋↓ | どれも IME が食べ、注目文節の文字が変わった |
| 英数キー（キーコード 102）、かなキー（104） | US 配列の本体でも合成でき、ABC ↔ ひらがな が切り替わった。入力中に英数を押すと、確定してから ABC になった |
| Control＋Shift＋K、Control＋Shift＋; | 食べたが何も変わらなかった（カタカナなどの入力モードを有効にしていないため、と見ている。未確認） |
| 候補ウインドウの撮影 | 変換候補、「読み」タブ、推測候補のどれも撮れ、読めた |

これだけで [macos.md](macos.md) の「資料に無い」のうち 1 つ（文字種変換のあと確定前の状態に留まるか）に答えが出ている。

## 5. この方法で採れないもの

| 採れないもの | 理由 | 代わりの方法 |
|---|---|---|
| Control＋Space、Control＋Option＋Space、Caps Lock、Fn / 地球儀キー、Command＋Control＋Space | システムがアプリより先に取る。プロセス内で合成したキーはそこを通らない | 方式 D（アクセシビリティの許可。未検証）か、人が押す |
| 押し続け（キーリピート）、修飾キーとの押し離しの順 | 合成では本物のキーボードの出方を再現しきれない | 記録だけのモードで人が押す |
| JIS キーボードに固有のキー（¥、_ など）の文字 | 本体が US 配列。イベントのキーボードの種類を JIS に偽れるかは未検証 | JIS キーボードをつなぐ |
| かな入力 | 入力ソース「日本語 - かな入力」を有効にしていない | 有効にしてから同じ方法で（未検証） |
| 再変換（確定済みの文字に Control＋Shift＋R、かなキー 2 回） | 試作のビューは選択範囲と確定済みの文字を IME に返す作りが最小限 | `attributedSubstring(forProposedRange:)` と `selectedRange` を正しく実装すれば採れる見込み（未検証） |
| 入力メニュー（メニューバー）からの操作 | 別プロセスの UI | 人が操作、またはアクセシビリティの許可で自動化（未検証） |
| ほかのアプリ（ブラウザ、Electron）での違い | 試験アプリは AppKit の標準の経路だけ | 必要になったら方式 D ＋ 画面の撮影 |

## 6. 人の手が要る作業

| 作業 | いつ | 回数 |
|---|---|---|
| 「画面収録とシステムオーディオ録音」の許可 | 候補ウインドウを初めて撮るとき | 1 回（済み） |
| アクセシビリティの許可 | 方式 D を使うとき（システムが取るキーを調べるとき）だけ | 1 回 |
| 設定の切り替え: ライブ変換、Windows風のキー操作、Shiftキーの動作、Caps Lockの動作、入力モード（カタカナ・全角英字・半角カタカナ・英字）の有効化 | 設定の組ごとに表を採り直す | 設定の組の数だけ |
| 本物のキーボードで押す（押し続け、Caps Lock、地球儀キー、押し離しの順） | 最後にまとめて | 数分 |
| 試験が終わったあと、設定を元に戻す | 最後 | 1 回 |

設定の切り替えを自動にできるか: 設定は `defaults` の `com.apple.inputmethod.Kotoeri` にある（`JIMPrefLiveConversionKey`、`JIMPrefPredictiveCandidateKey` などが見える）。
`defaults write` で書き換えて日本語入力プログラム（`JapaneseIM-RomajiTyping`）が読み直すか、「Windows風のキー操作」のキー名は何かは、未検証。
確かめ方は、人が設定画面で 1 つ切り替え、その前後で `defaults read` の差を見る。効けば、この行は「人の手」から外れる。

## 7. 注意

| 注意 | 理由 |
|---|---|
| 日本語入力プログラムは試験の変換を学習する | 試作で「辮かん」を 1 回確定しただけで、次から「へんかん」の第 1 候補が「辮」になった。確定は最小限にし、片付けは Esc でする |
| 学習を汚したくないなら、試験用のユーザアカウント（または macOS の仮想マシン）で動かす | 学習はユーザごと。戻す手段は設定の「変換学習: リセット」だけで、ふだんの学習も消える |
| 画面を撮る処理は、キーの処理が落ち着いてから呼ぶ | `screencapture` は別プロセス。試作ではメインスレッドで終わりを待った |
| 許可のダイアログが出ると、キーが試験の窓に届かなくなる | 試作で、撮影の最初の 1 回に system の窓（`UserNotificationCenter`）が開き、その間のキー 10 個ほどが変換中の文字列に入らなかった。1 件ごとの状態の確認で検知して止める |
| 実行中はキーボードとマウスに触らない | 試験アプリが前面でなくなると、日本語入力プログラムとのやり取りが切れる |
| 方式 D を使うときは、前面が試験アプリのときだけ送り、違えばその場で止まる | 別の窓にキーが行く（Windows 版の `lib.guard` と同じ） |
| 終わったら入力ソースを始める前のものに戻す | 入力ソースの切り替えはアプリの外にも残る |
| 実行時に標準エラーへ `error messaging the mach port for IMKCFRunLoopWakeUpReliable` が出る | 害は無かった（記録は正しく採れた） |

## 9. 作るもの

置き場所は `tools/keyprobe/mac/`（Windows 版と並べる）。

| ファイル | 中身 |
|---|---|
| `probe.swift` | 試験アプリ。`swiftc` で 1 ファイルをビルドする（Xcode のプロジェクトは作らない）。引数でキーの列を受け取り、JSON の行を標準出力に書く。記録だけのモード（人が押す用）も持つ |
| `seq.py` | `msime_tsf_seq.py` に当たる。キーの列を送り、キーごとの記録と候補ウインドウの画像を `out/` に出す |
| `table.py` | `msime_tsf_table.py` に当たる。状態 × キーの表を `out/mac_table.jsonl` に書く |
| `README.md` | 使い方と「してはいけないこと」（§7） |

- キーの書き方は Windows 版に合わせる（`kyouhaamedesu {Space} {Shift+Left}`）。修飾の名前は `Ctrl`・`Shift`・`Opt`・`Cmd`、キーの名前に `Eisu`・`Kana` を足す。
- 速さ: 試作は 1 キーごとに 0.45 秒待った。このままだと、状態 8 × キー 150 ほどの表は 1 つの設定の組につき 3 時間ほどかかる（1 件が状態作りを含めて 9 秒前後）。状態を作る文字の待ちを Windows 版並み（0.06 秒）に詰めれば 1 時間前後になる見込みだが、詰めて記録が崩れないかは未検証。
- 結果は [macos.md](macos.md) に「実機」の節を足して書く（[ms-ime.md](ms-ime.md) §1.5 と同じ形）。

進める順:

1. 試作を `tools/keyprobe/mac/` に整えて入れる（キーの列を送るコマンドまで）。
2. 既定の設定で、状態 × キーの表を採る。§8 の上半分が埋まる。
3. `defaults write` で設定が切り替わるかを確かめる（§6）。
4. 設定の組（ライブ変換、Windows風、Shiftキーの動作）ごとに表を採り直す。
5. 残り（システムが取るキー、押し続け）を、方式 D か人の手で確かめる。

## 10. 採らなかった方法

| 方法 | 採らない理由 |
|---|---|
| AppleScript（System Events の `keystroke` / `key code`）、cliclick | アクセシビリティの許可が要り、前面の窓に送るので事故の余地がある。採れる情報は方式 A より少ない |
| テキストエディットなど既存のアプリを相手にする | 変換中の文字列・文節・注目文節を外から読む手段が画面の撮影しかない |
| システム全体のアクセシビリティ API で候補ウインドウを読む | 許可が要る。画像で足りている。画像で読み違いが出たら検討する |
| Hammerspoon、Karabiner-Elements | キーを送る・見るだけで、IME の中の状態は見えない。常駐するものを入れることになる |
| XCUITest | Xcode のプロジェクトと試験の実行環境が要り、キーごとの細かい記録に向かない |
| InputMethodKit で確認用の IME を作る（Windows の確認用 TIP に当たる） | 見えるのは「IME がどう呼ばれるか」で、Apple の日本語入力プログラムの動きは分からない |
| Python（pyobjc） | 手元の Python に入っておらず、足すものが増える。Swift は Xcode に入っている |
