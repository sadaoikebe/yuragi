# macOS 版の設計方針

ゆらぎの macOS 版の方針。リポジトリ、開発環境、構成、キーボード、ハードル、Windows 版より良くできる点、進める順序を決める。詳細設計は範囲外。

確かさの印:

| 印 | 意味 |
|---|---|
| 〔リポジトリ〕 | このリポジトリのコード・文書で確かめた |
| 〔実機〕 | 開発機で確かめた（§9。Apple M1、macOS 27.2、簡易の署名） |
| 〔OS の仕様〕 | macOS の公開 API・公開されている仕様 |
| 〔未確認〕 | 確かめていない（§9.2） |
| 〔提案〕 | この文書の判断 |

---

## 1. 結論

| 問い | 答え |
|---|---|
| リポジトリ | 分割しない。`src/mac/` と `packaging/mac/` を足す（§2） |
| 開発機 | Apple シリコンの Mac 1 台で作れる（§3） |
| 構成 | 変換エンジン（`yuragi/`）はそのまま使う。TIP とブローカーに当たる部分を、InputMethodKit の入力プログラム 1 個（Swift）として書く（§4） |
| 最大のハードル | InputMethodKit はキーの解放を渡さない。イベントの監視（許可が要る）で採り、許可が無ければ押下だけで判定する（§6.1） |
| 配布のハードル | Developer ID の署名と公証。許可が署名に結び付くので、開発の早い段階から要る（§6.2） |
| US と JIS の混在 | イベントの監視で、打鍵ごとにキーボードの種類が採れる。設定も再起動もなしで打ち分けられる見込み（§5.1） |
| ほかの利点 | アプリの中で動く部品が無い、管理者権限なしで入る、OS の時刻が採れる、候補窓と設定を OS 標準の部品で作れる（§7） |

## 2. リポジトリ

分割しない〔提案〕。

| 理由 | 中身 |
|---|---|
| 共有物が大半 | エンジン（`yuragi/`）、配列とキーボードのデータ（`data/`）、キー割り当て（`yuragi/data/keymaps/`。`macos.json` を含む）、試験（`tests/`）、通信の仕様（DESIGN §3）〔リポジトリ〕 |
| 通信の互換 | 「項目を足すだけ」の規則（DESIGN「互換の規則」）を、エンジンと両方のフロントエンドの変更を 1 つのコミットで揃えて守れる |
| OS に依らない C++ | `src/broker/broker_core`（再起動の判断）と `src/tip/tip_logic.h`（食べるかどうか、返事の順序）を macOS 版からも使う〔リポジトリ〕 |
| 調査の資産 | macOS の日本語入力の実機調査（`docs/keybind/macos*.md`、`tools/keyprobe/mac/`）がここにある〔リポジトリ〕 |

### 足す場所

```
src/mac/            入力プログラム（Swift）
packaging/mac/      インストール・アンインストール、同梱ランタイムの依存の固定
data/keyboards/     既存のファイルに macOS のキーコードの列を足す（§5）
yuragi/             OS に依る箇所だけ分ける（下の表）
.github/workflows/  macOS（arm64）のジョブを足す
```

### エンジンの中の OS に依る箇所〔リポジトリ〕

| ファイル | Windows に依るもの | macOS 版での扱い |
|---|---|---|
| `yuragi/ime/broker_client.py` | 名前付きパイプ | Unix ドメインソケットの実装を足す（設定ウィンドウから入力プログラムへ） |
| `yuragi/ime/keyboard_setting.py` | `kbd101`／`kbd106` の判定 | 使わない（§5） |
| `yuragi/ime/power.py` | 電源の状態 | 足さない。電池のときに GPU を避ける規則は CUDA だけのもの |
| `yuragi/ime/learning.py` | ファイルのロック | 変えない。Windows 以外では POSIX のロックを使う |
| `yuragi/ime/admin_ui.py` | 窓まわりの Windows の呼び出し | §4.5 |
| `yuragi/ime/zenz.py`・`server.py` | LM の装置の候補 | MPS が候補に入っている（§4.4） |
| `yuragi/ime/host_win32.py` | 試験用の窓 | 対象外 |

変換の中身（`chord/`、`lattice/`、`session.py`）は OS に依らない。

### リリース

タグは Windows 版と共通の 1 系列にし、1 つのリリースに両方の配布物を添える〔提案〕。
macOS 版が実用になるまでは、macOS の配布物はプレリリースにだけ添える。README のインストール URL（`latest`）が指す Windows の正式版には影響しない。

## 3. 開発環境

| 要るもの | 用途 |
|---|---|
| Apple シリコンの Mac | 開発機 兼 実機。**対象は Apple シリコンだけにする**〔提案〕 |
| Xcode（Swift 6） | 入力プログラムのビルド、署名 |
| Python 3.12 以上 | エンジンと試験。同梱は Windows 版と同じ 3.13〔リポジトリ〕 |
| CMake（C++17 は Xcode の clang） | `broker_core`・`tip_logic.h` の試験 |
| PyTorch（arm64） | LM。MPS で GPU を使う |
| Apple Developer Program（年額の有料） | Developer ID の署名と公証（§6.2） |
| JIS キーボード（Mac 用と Windows 用） | §9.2 の JIS の問い |

- 入力プログラムは OS が起動するので、Xcode から直接は起動できない。デバッグは、動いているプロセスへの接続と記録で行う〔OS の仕様〕。
- 入力プログラムの試験は、ふだん使いとは別の利用者アカウントで行う〔提案〕。入力プログラムは利用者ごとに入り、壊れても別のアカウントの入力に影響しない。
- 同時打鍵の実地試験は、押下と解放をそのままの時刻で送るキーボードで行う。自分で文字の列を作って送るキーボード（プログラムできるもの）は、押下と解放が 1 ミリ秒間隔で届く〔実機〕。

## 4. 構成

### 4.1 Windows 版との対応

```
Windows:  アプリ ──[TIP DLL]──(名前付きパイプ)──[ブローカー]──(標準入出力)──[エンジン]
                    アプリの中                    利用者ごとに 1

macOS:    アプリ ══(OS の仕組み)══[入力プログラム]──(標準入出力)──[エンジン]
                                   利用者ごとに 1。TIP とブローカーを兼ねる
```

macOS の入力プログラムは、アプリの中ではなく、利用者ごとに 1 個の独立したプロセスで動き、アプリとの間は OS がつなぐ〔OS の仕様〕。

| Windows 版の部品 | macOS 版 |
|---|---|
| TIP（TSF、アプリごと） | 入力プログラムの中の、入力欄ごとのコントローラ（`IMKInputController`） |
| ブローカー（プロセスの見張り、配る） | 入力プログラムの中の見張り役。判断は `broker_core` を使う |
| 名前付きパイプ（TIP とブローカー） | 要らない。設定ウィンドウ用に Unix ドメインソケットを 1 本だけ持つ |
| エンジン（Python、標準入出力） | 同じ。通信も同じ（1 行 1 JSON）。子プロセスの起動は 40 ミリ秒、往復は 0.05 ミリ秒〔実機〕 |
| 設定ウィンドウ（tkinter） | §4.5 |

DESIGN「守ること」の 7 項目は、macOS 版でもそのまま守る。

### 4.2 入力プログラム（`src/mac/`）

| 役目 | 使うもの |
|---|---|
| 打鍵を受け取る | `IMKInputController` の `handle(_:client:)` と、イベントの監視（§6.1） |
| 変換中の文字を描く | `setMarkedText`（文節ごとの下線と注目文節）、確定は `insertText` |
| 候補窓・小さな表示 | フォーカスを取らないパネル（§7.3） |
| 入力モードの表示とメニュー | メニューバーの入力メニュー（入力モードのアイコン、`menu()` の項目） |
| 文書の左文脈 | クライアントの選択範囲と文字列の取得（§6.4） |
| エンジンの起動と見張り | `Process`＋`broker_core` |
| 設定ウィンドウとの通信 | Unix ドメインソケット（利用者だけが読み書きできる場所に置く） |

- **入力プログラムは落とさない。** 選ばれている間に落ちると、OS は起動し直さず、動いていたアプリは開き直すまでつながらない〔実機〕。落ち得る処理（変換、LM）はエンジンに置き、入力プログラムは薄く保つ。更新の手順は §6.3。
- **OS に依らない判断は書き直さない**〔提案〕。`broker_core` と `tip_logic.h` を、Swift の C++ 連携か薄い Objective-C++ の層を通して使う。
- **食べるかどうかは、Windows 版と同じ「食べる表」で即答する**〔提案〕。アプリは返事を待つので、打鍵 1 回で待たせる時間の上限（`KEY_BUDGET_MS`）と、間に合わなかったときの扱いも同じにする。
- Windows 版の `OnTestKeyDown` と `OnKeyDown` の二段構え、IMM 経由のアプリへの送り直しは無い。

### 4.3 入力モード

macOS には IME のオン・オフが無く、入力ソースを切り替える〔リポジトリ: keybind/macos-vs-windows.md〕。
ゆらぎは 1 つの入力プログラムの中に、入力モードを 2 つ持つ〔提案〕。

| 入力モード | Windows 版の対応 | メニューバーの表示 |
|---|---|---|
| ひらがな | かな入力 | ゆ |
| 英字 | 直接入力 | Y |

- カタカナ・全角英数などは、Windows 版と同じくエンジンの中の状態とする。
- 準備中・停止は、入力メニューの項目と小さな表示で知らせる。アイコンは使わない。入力プログラムが自分で切り替えられるのは一覧に見えるモードだけで、表示のためのモードを利用者の一覧に足すことになる〔実機〕。
- 英数キーは、最後に使った英字の入力ソースへ切り替える〔実機〕。ABC とゆらぎの英字モードを両方有効にしていると、英数 でゆらぎから外れることがある。

### 4.4 エンジン

`yuragi.engine` は macOS でそのまま動き、試験も通る〔実機〕。変えるのは次の 2 つ。

| 変えるもの | 中身 |
|---|---|
| キーコード | macOS のキーコードで届く打鍵を、キーの名前に直す（§5） |
| キーボード | 起動時に 1 つ決めるのをやめ、打鍵ごとに受け取る（§5） |

- LM の装置は、MPS で GPU 用のモデル、CPU で CPU 用のモデルの順に実測して選ぶ（CONVERSION「装置とモデル」）。M1 では MPS の medium が上限を超え、CPU の small になる（PERFORMANCE §5）〔実機〕。
- 同梱の Python は、移動できる形の CPython（arm64）を使う。版とハッシュを固定する規則は Windows 版と同じ。
- **将来の選択肢**: zenz を Python と PyTorch なしで動かす（llama.cpp や Core ML）。同梱物が小さくなり、起動が速くなる。最初の版では採らない。

### 4.5 設定ウィンドウ

最初の版は、tkinter の設定ウィンドウ（`admin_ui.py`）を macOS でも動かす〔提案〕。SwiftUI での作り直しは、その次の段とする（§7.3）。

### 4.6 置き場所

```
~/Library/Input Methods/Yuragi.app             入力プログラム。利用者の権限だけで置ける
~/Library/Application Support/yuragi-ime/      versions/<tag>/app、shared/runtime・dict・cache・model、staging
~/.yuragi-ime/                                 利用者のデータ。Windows 版と同じ名前・同じ形式
~/Library/Logs/yuragi-ime/                     記録
```

- 版ごとのフォルダ、共有物の再利用、試運転してから切り替える手順は、Windows 版と同じ考えで作る。
- `~/.yuragi-ime/` の学習履歴・個人辞書・設定は、Windows 版のファイルをそのまま持ち込める形式に保つ。
- レジストリ、Run キー、管理者権限の段は無い。入力プログラムは、選ばれたときに OS が起動する〔OS の仕様〕。

## 5. キーボード

### 5.1 US と JIS の混在

Windows は、日本語キーボードの設定（`kbd101` か `kbd106`）が PC 全体で 1 つで、変えるには再起動が要る〔リポジトリ: JIS.md §2〕。macOS は打鍵ごとに決められる。

| macOS の性質 | 確かさ |
|---|---|
| キーコードは、文字ではなくキーの物理的な位置を表す。JIS だけにあるキー（英数、かな、`¥`、`_`）には専用のキーコードがある | 〔OS の仕様〕 |
| イベントの監視で見えるイベントには、打ったキーボードの種類が付く。2 台を交互に打つと、打鍵ごとに変わる | 〔実機〕 |
| InputMethodKit に届くイベントでは、種類は常に 0 | 〔実機〕 |
| 種類の値から ANSI・JIS・ISO が分かる（`KBGetLayoutType`） | 〔OS の仕様〕。JIS の実物では〔未確認〕 |

**打鍵ごとに、そのキーを打ったキーボードの定義で文字を決める**〔提案〕。

- イベントの監視の許可が前提。許可が無いときは、設定で選んだ 1 つのキーボードとして扱う。
- エンジンは、打鍵に付いたキーボードを使う。通信には打鍵にキーボードの項目を足す（「互換の規則」に合う）。
- `data/keyboards/<名前>.json` の各行に、macOS のキーコードの列を足す。キーの名前・刻印・面の規則（JIS.md §2）は変えない。
- 種類で見分けられないキーボード（FMV-KB232 のように JIS と区別できないもの）は、接続されたキーボードごとに設定で選ぶ（§7.2）。

### 5.2 親指キー

| キーボード | 親指キー | 単独で押したとき |
|---|---|---|
| US | Space（左右とも） | 空白・変換 |
| Mac の JIS | 英数・Space・かな | 英数は英字へ、かな はひらがなへ |
| Windows 用の JIS | 無変換・Space・変換 | キーコードは〔未確認〕 |

- Mac の JIS は、Windows の JIS の無変換・Space・変換と同じ並びになる。親指キー 3 個の状態機械（[JIS-FSM.md](JIS-FSM.md)）と、「文字と組まなかった親指キーは IME の機能キーとして働く」規則を使う〔提案〕。
- **英数・かな は、押した時点で OS が入力ソースを切り替える。入力プログラムがキーを食べても止まらない**〔実機〕。親指キーにするには、「文字と組んだら、切り替わったモードを元に戻す」処理か、OS より前でキーを取る手段（イベントの監視でキーを書き換える。要る許可が増える）が要る。JIS キーボードの実機で決める。
- Caps Lock、地球儀キー、Control+Space、Command 付きのキーは、OS とアプリが先に使う〔リポジトリ: keybind/macos.md〕。

## 6. ハードル

### 6.1 キーを離した時刻

ゆらぎの同時打鍵の判定は、キーの押下と解放、その時刻を使う〔リポジトリ: DESIGN §3 の `down`／`up`〕。

| 経路 | 届くもの〔実機〕 |
|---|---|
| InputMethodKit | 押下、リピート、修飾キーの変化。**解放は届かない。** 時刻は実際より 4〜40 ミリ秒遅く、2 つのキーの解放より後に押下が届くこともある |
| イベントの監視 | 押下、解放、リピート、修飾キーの変化。実際の時刻、キーボードの種類。「入力監視」の許可が要る |

**イベントの監視で解放と時刻を採り、食べるかどうかは InputMethodKit で答える。許可が無ければ、押下だけで判定する**〔提案〕。

- 押下だけの判定は、状態機械に「解放が来ない」入力の形を足す。押下の間隔とリピートを使う。Space を離したのか、次のリピートの前なのかは分からない。
- 許可が無くても動き、許可すれば Windows 版と同じ精度になる。
- パスワード欄では OS がイベントの監視を止め、入力を英字に切り替える〔OS の仕様〕。ゆらぎはパスワード欄を自分で見分けなくてよい。

### 6.2 署名・公証・許可

| 事実 | 影響 |
|---|---|
| Apple シリコンでは、署名の無いコードは動かない。自分の Mac だけで通る簡易の署名は無料でできる〔OS の仕様〕 | 署名なしでは開発もできない |
| ブラウザーで取得した未公証のアプリは、OS が開くのを止める〔OS の仕様〕 | 配布には Developer ID の署名と公証が要る |
| 「入力監視」の許可は署名に結び付く。簡易の署名はビルドごとに別のアプリと見なされ、許可が外れる。古い許可の記録が残る間は、OS は許可を求める表示も出さない〔実機〕 | イベントの監視を使う開発は、Developer ID が無いと、ビルドのたびに記録を消して（`tccutil reset ListenEvent <バンドル ID>`）許可を採り直すことになる |
| 許可すると、OS が入力プログラムを起動し直す〔実機〕 | 許可の前後で変換中の文字を持ち越さない |

**イベントの監視を使う開発（段 1）から Developer ID で署名し、配布する版は公証する**〔提案〕。Python と PyTorch は入力プログラムのバンドルに入れず、`shared/` に置く（公証の対象が小さくなる）。

### 6.3 登録と更新

- **登録**: `~/Library/Input Methods/` に置くと入力ソースの一覧に現れ、`TISEnableInputSource`（入力プログラム、モードの順。逆だとモードは有効にならない）と `TISSelectInputSource` で有効にして選べる。ログアウトは要らない〔実機〕。
- **更新**: ほかの入力ソースへ切り替えてから、プロセスを止め、バンドルを置き換える。次に選ばれたときに新しい版が起動する〔実機〕。選ばれている間に止めない（§4.2）。切り替える前に、変換中の文字を確定する。

### 6.4 アプリごとの差〔実機〕

変換中の文字の表示、確定、文字の位置（候補窓の位置）、左の文字の取得は、次のどれでも動く。

| アプリ | 当てにしないもの |
|---|---|
| AppKit の標準のテキスト欄、Safari | なし |
| Chromium 系（Edge、VSCode などの Electron） | 文書の長さ（常に 0）、変換中の選択範囲（打鍵ごとに揺れる） |
| ターミナル | 左の文字（画面の文字が返る。プロンプトも入る）。属性は下線と背景色だけで、文節の番号は無い |

ターミナルでは左文脈を変換に使わない。文節の区切りは、どのアプリでも下線の太さで見せる。

### 6.5 ほかの道具との共存

キーを書き換える道具（Karabiner-Elements など）は、入力プログラムより手前で働く。ゆらぎは届いたキーをそのまま扱い、共存の保証はしない〔提案〕。

## 7. Windows 版より良くできること

### 7.1 構造から消える制約

| Windows 版の制約〔リポジトリ〕 | macOS 版 |
|---|---|
| キーボードの設定が PC 全体で 1 つ。変更に再起動 | 打鍵ごとにキーボードが分かる（§5.1） |
| TIP がアプリの中で動く。32 ビット用の DLL、サンドボックスのアプリ、管理者のアプリを個別に扱う | 入力プログラムは 1 個。アプリの種類を区別しない |
| パイプの相手の確認、アクセス権の設計 | 要らない（OS がつなぐ） |
| インストールに管理者の確認（UAC）、レジストリの登録 | 利用者の権限だけで入る |
| 開いたままのアプリに古い DLL が残る | 入力プログラムを置き換えれば全アプリが新しい版になる（§6.3） |
| TSF は打鍵の時刻を渡さない。TIP が処理した時刻を使う | イベントの監視で OS の時刻が採れる（§6.1） |
| パスワード欄を TIP が判定する | OS が切り替える（§6.1） |
| `OnTestKeyDown` で食べたキーを通せないアプリがあり、送り直す | 受け取りは 1 段 |
| 署名なしの DLL が Smart App Control に止められ得る | Developer ID と公証で正面から解ける（§6.2） |

### 7.2 キーボードまわり

- **キーボードごとの設定。** 接続されたキーボードごとに、配列（US・JIS・KB232 など）と親指キーを覚える。
- **US キーボードで親指キーを 3 個にする選択肢。** スペースバーの左右の Command を、文字と同時に押したときだけ親指キーとして扱う。Command は OS とアプリのショートカットに使うので、既定にはしない。

### 7.3 UI

**利用者に見える動きで迷ったら、macOS 標準の日本語入力に合わせる**〔提案〕。その実機調査は keybind/macos.md、macos-table.md〔リポジトリ〕。

| 項目 | macOS 版 |
|---|---|
| キー割り当ての既定 | 同梱の「macOS」プリセット（`macos.json`）。「MS-IME」「Japanist」も選べる |
| 候補窓 | AppKit／SwiftUI で作る。ライト・ダーク、Retina、アクセント色、文字の拡大は OS に任せる。注記・ページ・「Tab で選択」は Windows 版と同じ情報を出す |
| 入力モードの表示 | メニューバーの入力メニュー。入力欄の近くの表示は OS が出す |
| メニュー | 入力メニューに「設定を開く」「もう一度試す」を置く |
| 停止の通知 | OS の通知。フォーカスを取らない |
| 設定ウィンドウ | SwiftUI で作り直せば、実際のキーを押して選ぶ、接続中のキーボードを一覧する、といった操作を足せる |
| 再変換・確定の取り消し | macOS 標準にある操作（かな 2 回、Control+Shift+R）を足す〔未確認〕 |
| 更新 | アプリの更新の仕組み（Sparkle など）で、設定ウィンドウから更新する |

macOS のライブ変換と、候補ウインドウのタブ（読み・部首など）は、最初の版の対象外とする。

## 8. 進める順序

最初の版は US キーボードを対象にする。JIS は、実機で §9.2 の問いに答えてから足す。

| 段 | すること | 終わりの条件 |
|---|---|---|
| 1 | 最小の入力プログラム。同時打鍵でかなを入れ、変換中の文字を描き、確定する。エンジンは子プロセス。イベントの監視と、押下だけの判定 | テキストエディットで親指シフトの文が打てる |
| 2 | 変換の UI。文節、候補窓、予測、「macOS」プリセット、入力モード | 日常の文章が打てる |
| 3 | 見張り、設定ウィンドウ、打鍵ごとのキーボード、キーボードごとの設定 | DESIGN §9 に当たる実地試験が通る |
| 4 | インストール・更新・アンインストール、公証、プレリリース | 別の Mac に入れて使える |
| 5 | macOS らしい UI（SwiftUI の設定、再変換、更新の仕組み） | — |

## 9. 実機の確認

道具は `tools/keyprobe/mac/imk/`（記録するだけの入力プログラム。[使い方](../tools/keyprobe/mac/imk/README.md)）。

### 9.1 確かめたこと

条件: Apple M1、macOS 27.2、内蔵の US キーボード（種類 91）と外付けの US キーボード（種類 40）、簡易の署名。本文の〔実機〕はこの表を指す。

| 項目 | 事実 |
|---|---|
| InputMethodKit に届くイベント | 押下、リピート（印が付く。0.5 秒後から 0.083 秒ごと）、修飾キーの変化（1 回につき 2 度）。解放は `recognizedEvents` で求めても届かない。キーボードの種類は 0、時刻は実際より 4〜40 ミリ秒遅い |
| イベントの監視 | 入力プログラムのプロセスから使える。解放、実際の時刻、キーボードの種類、送り元のプロセスが採れる |
| 許可 | §6.2 の表 |
| 英数・かな | OS が先に入力ソースを切り替え、そのあと押下が届く。食べても切り替わる。英数 の行き先が ABC のときは、入力プログラムが外れて英数 は届かない（合成したキーで確認） |
| エンジン | Python 3.13 と torch 2.9.1 で、Python と C++ の試験が通り、`yuragi.engine` が MPS を含めて装置を選んで変換する |
| 子プロセス | Python を起動して標準入出力で話せる。起動 40 ミリ秒、往復 0.05 ミリ秒 |
| 登録と更新 | §6.3 |
| モードの切り替え | 入力プログラムは `selectMode` で、有効で一覧に見えるモードへ切り替えられる。一覧に見せないモードは、有効にも選択にもできない |
| アプリごとの差 | §6.4 |
| 選ばれている間のプロセスの停止 | OS は起動し直さない。動いていたアプリは、入力ソースを選び直しても、プロセスを手で起動しても、つながらない。新しく起動したアプリと、開き直したアプリはつながる |
