# JIS 106 対応の実装仕様

## 1. 対象

| キーボード | Windows のキーボード設定 | かな配列 |
|---|---|---|
| `ansi101` | 英語（`kbd101`） | NICOLA-A |
| `jis106` | 日本語（`kbd106`） | NICOLA-J |

親指キーは Space・無変換・変換の 3 個。親指がどれを押したかを証拠として残し、同時打鍵では左右の面から変換が選ぶ。文字と組まなかった無変換・変換は IME の機能キーとして働く。判定の仕様は [JIS-FSM.md](JIS-FSM.md)。物理位置、刻印名、文字面、局面ごとの既定は [JIS-LAYOUT.md](JIS-LAYOUT.md) を実装基準とする。

## 2. キーボードで変わるもの

キーボードで変わるのは、届いたキーをどの文字にするかだけである。キー表、親指キー、同時打鍵の判定、割り当ての規則はキーボードによらない。

1. **キーボードのデータは 1 ファイル。** `data/keyboards/<名前>.json` に、文字キーを 1 個 1 行で書く。行は、仮想キーコード、刻印（Shift なしで打つ文字）、Shift で打つ文字、英数で打つ半角の文字（刻印と違うときだけ）。かなの面は、ファイルの `kana` が指す NICOLA の表から引く。表に無いキー（JIS の `:` `]` `\`）は、かなでは何も入力しない。キーボードを足すときは、ファイルを 1 つ足す。
2. **面は文字の規則で決める。** キーボードごとの例外は持たない。
   - かなの Shift は、英字なら大文字の半角、それ以外はその文字の全角。引用符は MS-IME と同じく `”` `’` にする。Shift の文字が空のキー（JIS の Shift+0）は何もしない。
   - 英数の全角は刻印の全角（`¥` は `￥`）。
3. **和音はキーの名前で持つ。** 届いた仮想キーコードを、セッションのキーボードでキーの名前に直してから表を引く（[KEYBIND.md](KEYBIND.md#41-和音の書き方) §4.1）。キー表は 1 枚で、今のキーボードに無いキーの行は、どのキーにも当たらない。文字キーかどうかも名前で決まる。TIP に渡す食べる表だけは、キーボードの仮想キーコードに直して作る。
4. **キーボードはエンジンが起動時に決め、セッションが持つ。** Windows の日本語キーボードの設定（`kbd101` か `kbd106`）は PC 全体で 1 つで、変えるには再起動が要る。エンジンは起動時に、読み込み済みの日本語のキーボード配列（`GetKeyboardLayoutList`）でスキャンコード `0x1A` の VK を引き（`MapVirtualKeyExW`）、`0xC0` なら `jis106`、それ以外と日本語の配列が無いときは `ansi101` とする。配列を新たに読み込まないので、利用者の言語の一覧は変わらない。結果は記録に `keyboard:` で残し、すべてのセッションがこのキーボードを使う。キー設定はキーボードを知らない。キー設定画面のキー追加も同じ判定を使う。
5. **親指キーは固定。** どのキーボードでも Space・無変換・変換。US キーボードには無変換・変換が無いので、US での動きは変わらない。

Windows の設定とキーボードの対応は次のスキャンコードで見分けられる。

| スキャンコード | ANSI の VK | JIS の VK |
|---|---:|---:|
| `0x1A` | `0xDB` | `0xC0` |
| `0x27` | `0xBA` | `0xBB` |
| `0x29` | `0xC0` | `0xF3` |

## 3. TIP とエンジンの接続

- TIP の文字キーの判定は、エンジンが食べる表の `characters` で送るキーボードの文字キーで行う（[KEYBIND.md](KEYBIND.md#71-食べる表) §7.1）。JIS の `VK_OEM_102` もこれで入り、US では入らない。TIP はキーボードを自分では判定しない。IME 用のキーも、Windows が届けた VK のまま和音にする（[KEYBIND.md](KEYBIND.md#41-和音の書き方) §4.1）。Windows の Caps Lock、かなロック、その他の専用ショートカットが、単独の IME キーとして再解釈されないようにする。[WDK の NLS 表](https://github.com/microsoft/Windows-driver-samples/blob/main/input/layout/fe_kbds/jpn/106/kbd106.c#L467-L571)
- JIS の Alt+半角/全角は、修飾を問わない `VK_KANJI` の PreservedKey で受ける。Alt を先に押せば、どちらを先に離しても 1 回届く。そのあと通常のキーの経路に届くのは `VK_KANJI` の解放だけなので、同じ打鍵が重ねて実行されることはない。半角/全角を先に押すと、Alt+半角/全角ではなく半角/全角として届く（`keyprobe` の `jis-kanji`）。対象外の入力欄、フォーカス移動、キーの送り直しには既存の規則を適用する。[PreserveKey](https://learn.microsoft.com/en-us/windows/win32/api/msctf/nf-msctf-itfkeystrokemgr-preservekey) [Windows のキー入力](keybind/windows.md)
- CMake が既定キー表を `ansi101` で Python の表から生成する。TIP は接続前はこれを使い、エンジンの表が届いたら置き換える。`characters` の無い表（古いエンジン）は受け取らず、既定表のままにする。
- 通信にキーボードの項目は足さない。TIP とエンジンは同じ PC の同じ設定に従うので、食い違わない。Caps Lock は `caps_lock` を打鍵に付け、省略時はオフとする。

## 4. 検証

| 段階 | 確認すること |
|---|---|
| エンジンとキー表 | ANSI の既存テストに加え、JIS の文字キー 48 個の全ての面、106 キーの分類、刻印名の読み書きを確認する。`;` の `ん`・`っ`、`@` の読点と空欄面、`[` の濁点・半濁点、数字段の親指面、`Shift+0`、`¥` と `\` の幅、Caps Lock と F9/F10 を確認する。候補番号とテンキー、Space の単独・前押し・後押し、空欄面が未確定を保つことも含める |
| Windows と TIP | `kbd101` と `kbd106` で、エンジンの記録の `keyboard:` と、TIP が `VK_OEM_102` を送るかを確認する。`kbd106` の TSF RichEdit と IMM の対象窓で、修飾を先に押す場合と本体を先に押す場合を二通りの解放順で試し、特殊キーの down/up と PreservedKey を確認する。通す修飾付き打鍵が別のモード切替に化けないこと、フォーカス切り替え、IME オフからの起動も確認する。新 MS-IME の標準テンプレートを参照し、半角/全角と英数の直後の確定・挿入をキー表と照合する |
| 親指キーの判定 | [JIS-FSM.md](JIS-FSM.md) §13 の 2 つの確認を試験にする。モデルに従う打鍵で左右の確定と交互が実際の親指と合うこと、任意の打鍵列で状態と内部の値が合うこと。セッションでは、無変換・変換の同時打鍵が片側の面に決まること、遅れて届いた証拠で表示が変わること、単独の無変換・変換が局面の割り当てを実行することを確認する |
| JIS 実機での受け入れ | JIS 固有キーを実際に打ち、Space・無変換・変換の同時打鍵、各キーの打ち心地を確認する。1 回の親指打鍵が 2 個のキーを押すときのずれを記録し、`JOIN_MS` と照合する。JIS でも通常の [DESIGN の実地試験](DESIGN.md#9-実地試験) を通す |

Windows 側の確認には、ANSI 101 を接続して Windows を 106 設定にし、`keyprobe` で JIS 専用キーのスキャンコードを送る方法を使える。合成打鍵は対象窓を確認してから送る。NLS の仮想キーが押下状態に残る場合は、検証窓を英語入力に切り替え、残っている VK に解放を送ってから終了する。[keyprobe の使い方](../tools/keyprobe/README.md)

配列を追加したら、暖機・自己診断・かなから打鍵を作る評価・記録の配列名を同じプロファイルに通す。配布物に JIS の表が入り、32/64 ビットの TIP がそれぞれ既定表を読めることを確認する。利用者向けの README・USAGE には対象配列、Windows の設定、JIS の打ち方を記載する。

## 5. 親指キーの接続

Space・無変換・変換は同じ規則で動く。押し方で 3 通りに分かれる。

| 押し方 | 起きること |
|---|---|
| そのキーだけを押す | そのキー本来の機能（[JIS-LAYOUT.md](JIS-LAYOUT.md) §4.1 のそのキーの行） |
| 文字キーとほぼ同時に押す | 親指シフトになる。文字キーの親指面が入り、そのキー本来の機能は働かない |
| Shift・Ctrl・Alt を押しながら押す | その組み合わせの機能。親指シフトにはならない |

親指シフトになったとき、Space だけなら左右は変換が選び、無変換が押されていれば左、変換が押されていれば右の面に決まる。機能の割り当ては変えない。

同時打鍵の判定そのものは [JIS-FSM.md](JIS-FSM.md) に従う。ここでは、その入力と出力を、キーボード・セッション・TIP・プロトコルにつなぐ規則を定める。

### 5.1 親指キー

- `keys.THUMBS` が、仮想キーから状態機械のキー名への対応を持つ。キーボードによらない。どの親指が押すキーかは `fsm.py` の `THUMB_SIDE` が持ち、状態機械と変換の両方がそれを使う。

| VK | キー名 | 押す親指 |
|---:|---|---|
| `0x20` | `space` | どちらも |
| `0x1D` | `muhenkan` | 左 |
| `0x1C` | `henkan` | 右 |

- `Keyboard.classify` は親指キーを `("O", キー名)` として返す。`Chord.typing` は、修飾なしの親指キーを打鍵層に含める。
  打鍵層のキーは、今の Space と同じく「常時」と直接入力の局面には割り当てられず、食べる表にも入らない。
- Shift・Ctrl・Alt を伴う無変換・変換は、今の Shift+Space と同じく状態機械に入れず、局面の割り当てを押下の時点で実行する。

### 5.2 状態機械に入れる条件

修飾なしの親指キーは、文字キーが状態機械に入る間は、どの局面でも状態機械に入れる。変換中・候補選択中・予測候補選択中も同じである。
入力のない局面でも入れる。親指を先に押す同時打鍵が、そこから始まるからである。

文字キーが状態機械に入らない間は、同時打鍵が起きないので、次のように扱う。

| 状況 | Space | 無変換・変換 |
|---|---|---|
| 直接入力 | 通す（今と同じ） | 通す |
| 全角英数入力 | 全角空白（今と同じ） | 押下の時点で局面の割り当てを実行する |
| 英数の続き | 今の分岐（半角空白、または単独打鍵として扱う） | 押下の時点で局面の割り当てを実行する |

状態機械に入れた親指キーの VK は `_fsm_down` に入れ、解放も状態機械に渡す。入れなかったキーの解放は渡さない。

### 5.3 単独打鍵

- `ThumbTap(key)` を受けたら、その時点の局面で `key` の VK の割り当てを引いて実行する。Space は今と同じで、無変換・変換は [JIS-LAYOUT.md](JIS-LAYOUT.md) §4.1 の行を使う。
- 機能が働くのは、キーを離した時点か、押してから 80 ms の時点である。Space と同じ遅れが無変換・変換にも付く。
- 文字なしで親指キーを 2 個続けて押したときに働くのは、最初のキーの機能 1 回である（JIS-FSM.md §12）。
- 割り当てが「通す」の単独打鍵は、判定が決まった時点でアプリに渡す。押下の時点では TIP が食べているので、エンジンは判定が決まった入力（解放または期限）の返事でそのキーを指定し、TIP が送り直す（[KEYBIND.md](KEYBIND.md) §7.6 と同じ印を付ける）。
  既定で該当するのは、入力のない局面の変換（再変換の予約）だけである。
  セッションは、送り直すキーを `key_resend` に、TIP が実行するコマンドを `key_global` に記録する。これを解放や期限の返事に載せる項目は、プロトコルの作業で決める。
- Space の単独打鍵は今と同じで、「通す」や TIP が実行するコマンドは割り当てられない。
- リテラルや編集のキーが来て判定を閉じるとき（`_finish_pending`）は、今と同じく期限の経路で先に解決する。未使用の無変換・変換は、そこで単独打鍵として働く。

### 5.4 証拠からトークンへ

`to_lattice_token` が `AmbShift` の `struck`・`held`・`over` から左右を導く（JIS-FSM.md §9）。

1. 左右が確定したら、その側の面だけを `faces` に残す。確定しなければ、両方の面を残す。
2. そのあとは今と同じである。面が残らなければ何も入力しない。残った面が記号 1 種類ならリテラルにする。かなの面が 1 つなら `shift`、2 つなら `amb` とする。
3. `press` と `turn` は今と同じ形で付ける。交互の規則（`alternation.py`）は変えない。確定した打鍵は「面が片側だけのキー」と同じ道で、押下の向きを決める。

`press` の意味は「1 回の Space の押下」のままである。Space に触れなかった無変換・変換だけの同時打鍵は、自分だけの `press` を持つ。

### 5.5 後から届く証拠

`ThumbJoin` と `ThumbOver` は、出力済みの `AmbShift` に証拠を足す。

- `AmbShift` は、状態機械が付けた元の `(press, turn)` を、書き換えない項目として持つ。照合はこれで行う。
  `press` は、記号の同時打鍵（`_press_alias`）と挿入（`_split_press_at`）で付け替わるので、照合には使えない。
- 対象の `AmbShift` が未確定のトークン列にあれば、`struck` または `over` に足す。なければ捨てる（確定済み、削除済み、空欄面で捨てた打鍵、リテラルになった打鍵）。
- 足した結果、確定した側の面が空欄になった打鍵は、トークン列から除く。
- 確定した側の面が空欄で何も入力しなかった打鍵も、同じ押下の残りには向きを伝える。その向きを持ち越し（`_carry`）に入れる。
- 足した証拠が、部分確定や挿入で持ち越した向き（`_carry`）と矛盾したら、その押下の持ち越しを捨てる。証拠を優先する。
- 反映したら候補を捨て、未変換なら表示を作り直す。文節内入力では、入力中の文節を作り直す。それ以外の変換済みの表示は変えない。
  変換済みの打鍵に証拠が届くのは、同時打鍵と変換の間に `reset` も単独打鍵も挟まらない場合だけで、今のキー操作では起きない。
- `ThumbOver` は同じ入力の `ThumbTap` より前に届く。単独の変換・Space で変換するときは、証拠が入った後のトークン列を変換する。

部分確定の持ち越し、押下の分割、記号の同時打鍵による押下の区切りは、今の処理をそのまま使う。どれも `press` の番号と向きだけを見ており、番号の付け方が変わっても成り立つ。

### 5.6 判定を閉じる

| セッションの処理 | 状態機械の入力 | 押されている親指キーの記録 |
|---|---|---|
| `_finish_pending`（リテラル、編集キー、コマンド） | `reset` | 残す。キーは押されたままで、解放も届く |
| `_reset_input`（フォーカスの喪失、取り消し、エラー後の作り直し） | `clear` | 消す。`_fsm_down` も空になり、解放は届かない |

### 5.7 TIP とプロトコル

- TIP は、かな入力中の修飾なしの無変換・変換を、Space と同じく打鍵層のキーとして食べ、押下と解放の両方をエンジンに送る。TIP の打鍵層の判定（`Typing`）に、修飾なしの無変換・変換を含める。
- 判定のタイマーは今の `timer` の項目だけで足りる。`JOIN_MS` の判定は、キーが届いた時点の時刻の比較で行う。
- 変換・無変換は押下と解放が普通に届く（`keyprobe` の `jis-codes`）。
