# ゆらぎの全体設計（TIP・ブローカー・エンジン、置き場所、インストール）

ゆらぎを構成するプロセス、その間の通信、ファイルの置き場所、インストールの手順、利用者に見えるものの仕様。
コードと試験のコメントは、この文書の節番号（§5.4 など）を参照している。節番号を変えるときは、
コード側の参照も直す。

**読み方**: §1〜§3 が考え方、§4〜§8 が部品ごとの仕様、§9 が画面と文言、§10 が試験と合格条件。
仕様の中の数値は §11 の定数表にまとめてある。変換の中身（打鍵の判定、変換、候補、学習）は
[CONVERSION.md](CONVERSION.md)。

---

## 1. 何を約束するか

利用者から見た約束。設計はこれを満たすためにある。

| # | 約束 |
|---|---|
| P-1 | **打った文字は消えない。** 変換エンジンに何が起きても、画面に出ていた文字は残る |
| P-2 | **エンジンが落ちても、数秒の「間」で済む。** 利用者は何もしなくてよい |
| P-3 | **直らない故障は、1 回だけ、普通の言葉で知らせる。** 「もう一度試す」がそこにある |
| P-4 | **勝手にウィンドウを出さない。フォーカスを奪わない。** 例外なし |
| P-5 | **PC に掛ける負荷に上限がある。** プロセスの起動回数も、待ち時間も、ファイルの大きさも |
| P-6 | **使い込んでも遅くならない・壊れない。** |
| P-7 | **入れる・上げる・消すは、アプリを開いたままで終わる。** 途中で失敗したら元のまま |

### 設計の前提にした実測（開発機）

| 項目 | 値 | 意味 |
|---|---|---|
| 辞書の読み込み（キャッシュあり） | 2.35 秒 | エンジンの起動し直しは 3〜4 秒かかる。この間をどう見せるかが設計の中心 |
| エンジンのメモリ（辞書のみ、LM 別） | 1,260 MB | 重い。最大の弱点（§12） |
| 起動後、最初の 1 回の変換 | 617ms | 2 回目以降は 9ms。温めないと起動直後の最初の打鍵が時間切れになる（§6.3） |
| 変換時間と入力の長さ | 50 字 9ms／200 字 38ms／400 字 98ms | 長さに比例。上限 200 字なら余裕がある（§6.5） |

## 2. 考え方

### 2.1 起動し直しを決めるのは 1 人だけ、回数は決まっている

エンジンの起動し直しを決めるのは、PC に 1 つのブローカー（§5）だけ。短い間に落ちた回数を数え、見えないところで行う。
TIP はプロセス管理をしない（§7.1）。

### 2.2 壊れやすいものほど内側に、頑丈なものほど外側に

```
アプリ ──[TIP DLL]──(名前付きパイプ)──[ブローカー]──(標準入出力)──[変換エンジン]
          薄い・状態が少ない          小さい・ネイティブ        大きい・Python・1.2GB
          アプリの中で動く            落ちない前提で作る        落ちることを前提に扱う
```

- **TIP** は他人のアプリの中で動く。ここで間違えるとアプリを巻き込む。だから**できることを減らす**:
  打鍵を送る、返事を画面に書く、それだけ。プロセス管理・再試行・ファイル読み書きは持たない。
- **変換エンジン**は大きく、辞書・学習・LM・torch を抱える。落ちる可能性が一番高い。だから
  **落ちても誰も困らない位置**に置く。エンジンと直接話すのはブローカーだけ。
- **ブローカー**はその間に立つ小さな常駐プログラム（C++）。エンジンを起動し、見張り、
  落ちたら起動し直す（短い間に 3 回落ちたら止める）。エンジンが使えない間の打鍵は預からず、
  TIP がそのままアプリへ通す（一般的な IME が準備中にする扱い）。

TIP は TSF の中でしか動かず、試験しにくい。ブローカーは**ただの exe なので、CI で落とす・固める・殺す
試験が書ける**。生存管理をブローカーに置くのはこのため。

### 2.3 状態を増やさない

頑丈さは、回復の仕組みを足すことではなく、**取りうる状態を数えられるほど少なくする**ことで得る。
利用者に見える状態は 4 つだけ（§9）。エンジンの起動失敗の原因が何通りあっても、
利用者に見える結果は「数秒待つと直る」か「1 回知らせて止まる」の 2 つしかない。

採らない案:

- *打鍵の記録を取っておき、エンジン復帰後に再生して変換中の状態を完全に復元する。*
  「再生したらまた同じ所で落ちる」場合の扱いなど状態が増える。代わりに
  **「落ちたら、見えている文字をそのまま確定する」**（P-1 は守れる。失うのは、その 1 回の再変換の機会だけ）。
- *エンジンが動かないとき用に、TIP の中に簡易かな入力を持つ。* 打鍵の判定ロジックが二重になる。
- *セーフモード（設定を無視して起動し直す）。* 設定・個人辞書・学習の各ファイルを「壊れていても起動できる」
  ように読むので不要（§6.2）。

## 3. 守る条件（試験で数える）

| # | 条件 | 数え方 |
|---|---|---|
| I-1 | TIP が起動してよいのはブローカーだけ。ブローカーの二重起動防止と接続の間隔（2 秒）で頻度を抑える | プロセス生成の記録 |
| I-2 | エンジンが 10 分間に 3 回落ちたら止まり、利用者の操作かサインインまで再開しない | 同上 |
| I-3 | 新しく現れるウィンドウは 0 枚（利用者がメニューや通知を押して開いたものを除く）。どのプロセスもコンソールなしで起動する | 起動のしかた（§5.3）の確認 |
| I-4 | TIP が打鍵 1 回で UI スレッドを止める時間は最大 200ms | 計測 |
| I-5 | インストール・更新・削除は、どこで失敗しても「前の版が動く」か「新しい版が動く」 | 途中で止める試験 |
| I-6 | 「成功」「OK」と表示するのは、結果を読み返して確かめたあとだけ | コードレビュー |
| I-7 | 利用者のデータ（学習履歴・個人辞書・設定）を、頼まれずに消さない | 同上 |

## 4. 全体の構成

### 4.1 プロセス

| 部品 | 実体 | 数 | 誰が起動するか |
|---|---|---|---|
| TIP | `yuragi_tip.dll`（C++） | アプリのスレッドごと | Windows |
| ブローカー | `yuragi-broker.exe`（C++、ウィンドウなし） | サインインごとに 1 | サインイン時（Run キー）。無ければ TIP が条件付きで（§7.3） |
| エンジン | 同梱 Python で `python -m yuragi.engine` | ブローカーごとに 1 | ブローカーだけ |
| 設定ウィンドウ | `pythonw -m yuragi.ime.admin_ui` | 利用者が開いたとき | ブローカー（TIP のメニューから依頼） |

### 4.2 置き場所

```
%ProgramFiles%\yuragi-ime\<tag>\          管理者だけが書ける。全アプリに読み込まれるものはここ
    yuragi_tip.dll  yuragi-broker.exe  elevated.ps1

%LOCALAPPDATA%\yuragi-ime\                 利用者の権限で動くものだけ。管理者権限では決して実行しない
    versions\<tag>\app\                     Python のソース
    versions\<tag>\engine.json              このタグが使う共有物への道順（ブローカーが読む）
    shared\runtime\<id>\                    同梱 Python + tkinter + torch + 依存。id = 版とハッシュ
    shared\dict\<上流コミット>\             Mozc 辞書
    shared\cache\<辞書マニフェストのハッシュ>.pkl
    shared\model\<リビジョン>\              LM モデル
    staging\                                更新の作業場。成功したら versions へ移す

%USERPROFILE%\.yuragi-ime\                 利用者のデータ。更新でもアンインストールでも触らない
    config.json  tip.json
    learning.jsonl  personal_lexicon.jsonl
    logs\broker.log  logs\engine.log  logs\notices.log（それぞれ前の世代 *.prev.log）

HKLM  CLSID・TIP 登録 → %ProgramFiles%\yuragi-ime\<tag>\yuragi_tip.dll
HKCU\Software\yuragi-ime   Tag = <tag>     「この利用者には、この版が入っている」の唯一の印
HKCU\…\CurrentVersion\Run   yuragi-ime = "…\<tag>\yuragi-broker.exe"
```

要点:

- **版ごとにフォルダを分ける。** 更新は「新しいフォルダを作って、登録を付け替える」だけで、
  読み込まれている DLL には触らない。だからアプリを開いたまま更新できる（P-7）。
- **大きいもの（ランタイム・辞書・モデル）は中身で名前を付けて共有する。** 中身が同じなら更新で取り直さない。
- **学習履歴と個人辞書はプログラムのフォルダの外**（`%USERPROFILE%\.yuragi-ime\`）に置く。
- **Python の経路は同梱ランタイム 1 本。** ほかの Python を探さない。

## 5. ブローカー（`src/broker/`）

### 5.1 役目

1. エンジンを起動し、見張り、落ちたら起動し直す（§5.4）。
2. TIP からの接続を受け、打鍵をエンジンに渡し、返事を返す。
3. エンジンが使えない間に届いた打鍵には、すぐ「使えない」と返す（§5.6。TIP が素通しにする）。
4. 止まったことを、利用者に 1 回だけ知らせる（§9.3）。

やらないこと: 変換の中身を理解すること。メッセージは `sid` と `seq` を見て配るだけ。

### 5.2 起動と終了

- サブシステムは WINDOWS（コンソールを持たない）。ウィンドウは通知用の非表示ウィンドウ 1 枚だけ。
- 二重起動は名前付きミューテックス `Local\yuragi-ime-broker` で防ぐ。取れなければ黙って終了コード 0。
- 起動したら `HKCU\Software\yuragi-ime\Tag` を読み、自分のタグと違えば黙って終了（古い版が残っていた場合。
  この利用者に入っていなければタグが無いので、やはり終了する）。
- 保守中（§8.1）はブローカーを起動しない側（TIP、§7.3）が確かめる。インストーラは動いているブローカーに
  `quit` を送る。
- 終了するのは: パイプで `quit` を受けたとき（インストーラ）、サインアウト。

### 5.3 エンジンの起動のしかた

`CreateProcessW` で、次のとおり。

- 実行ファイルは `engine.json` に書いてある絶対パスの `python.exe` だけ。**無ければ起動しない。別の Python は探さない。**
- フラグは `CREATE_NO_WINDOW`。同梱ランタイムの `python.exe` はランチャーを挟まないので、子も孫もコンソールを作らない。
  > **注意**: venv の `Scripts\python.exe` はランチャーで、本物の Python を子として起動し直す。
  > `CREATE_NO_WINDOW` などのフラグはその子に届かず、コンソールのウィンドウが出る。venv の経路を戻さない。
- 環境変数は**引き継がない**。`CreateEnvironmentBlock` で利用者の既定の環境を作り、
  `PYTHONUTF8=1` `PYTHONIOENCODING=utf-8` `PYTHONNOUSERSITE=1` `HF_HUB_OFFLINE=1` を足し、
  `PYTHONPATH` `PYTHONHOME` を消す。
- 標準入力・標準出力は無名パイプ（ブローカーとの通信）。標準エラーは `logs\engine.log`
  （起動のたびに前の分を `engine.prev.log` に回す。1 本の上限 1MB）。
- 「ブローカーが死んだら子も死ぬ」ジョブ（`JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE`）に入れる。孤児を残さない。
- 作業フォルダは `versions\<tag>\app`。

### 5.4 エンジンの見張り

```
            ready 受信
 STARTING ───────────────► READY
    ▲  │                     │
    │  │ 終了（無応答で強制終了を含む）
    └──┴─────────────────────┘  10 分間に 3 回目の終了なら ──► FAILED
                                                                  │
 STARTING ◄──────(利用者が「もう一度試す」／次のサインイン)────────┘
```

- **終了の検知**はプロセスのハンドルを待つ（ポーリングしない）。
- **無応答の検知**: エンジンに渡した要求の返事が `ENGINE_HANG_MS` 来なければ、エンジンを強制終了して
  「終了」と同じ扱いにする。エンジンは必ず即答する作りなので（LM 待ちは `pending` で即答）、これは故障。
- 終了したら、すぐ起動し直す。ただし `ENGINE_EXIT_WINDOW_MS`（10 分）の間の `ENGINE_MAX_EXITS`（3 回）目の
  終了なら FAILED に入り、§9.3 の通知を 1 回出す。**以後、自分からは何も起動しない。**
  終了コードと `logs\engine.log` の最後の `fatal` 行は `broker.log` に残す（利用者への文言は 1 種類）。
- 利用者の「もう一度試す」（設定を変えたあとの再起動も同じ）は、数えた回数を 0 に戻して起動する。

これで「10 分間に最大 3 回、ウィンドウなし」が上限になる（I-2）。

### 5.5 TIP との通信（名前付きパイプ）

- 名前: `\\.\pipe\yuragi-ime-<利用者の SID>-<セッション番号>`。バイト単位、1 行 1 JSON（UTF-8、`\n` 区切り）。
- アクセス権: その利用者に読み書き。加えて「すべてのアプリパッケージ」（`S-1-15-2-1`）に読み書き
  ——スタートメニューの検索欄など、サンドボックス内のアプリからも**接続だけは**できるようにする。
  他の利用者・ネットワークからは不可（`PIPE_REJECT_REMOTE_CLIENTS`）。
- TCP・ポート番号・トークンは使わない。パイプが在ること自体が「ブローカーがいる」の印になる。

**メッセージ（プロトコル 1）**

TIP → ブローカー:

```json
{"op":"hello","proto":1,"tag":"v0.2.0","bits":64,"passes":true}
{"seq":17,"op":"down","vk":74,"t":123456,"mods":[]}        ← op は down/up/timeout/reset/set_direct
{"op":"retry"}                                              ← 利用者が「もう一度試す」を選んだ
{"op":"open_admin"}                                         ← 設定ウィンドウを開く
{"op":"quit"}                                               ← インストーラだけが使う
```

ブローカー → TIP:

```json
{"proto":1,"state":"ready","warnings":[]}                   ← hello の返事
{"seq":17, …エンジンの返事の全項目… }                      ← 要求の返事（エンジンの返事に seq を付けたもの）
{"seq":17,"state":"starting"}                               ← 起動中／FAILED 中（"down"）。この打鍵は処理されなかった
{"seq":17,"pass_through":true,"direct":false}               ← 同上。hello に passes の無い TIP へ（§5.6）
{"event":"state","state":"starting"}                        ← 状態が変わった（要求と無関係に届く）
{"event":"reset"}                                           ← エンジンが終了した。変換中のものは失われた
```

`state` は `ready` `starting` `down` の 3 つ。hello の `passes:true` は「`ready` でない間の打鍵を TIP が自分で素通しにする」の印。

**互換の規則**（更新後も、開いたままのアプリには古い DLL が残るため必須）:

- 受け取る側は、**知らない項目を無視し、無い項目は既定値にする。** 項目の数や余分を検査しない。
- プロトコル 1 の中での変更は「項目を足す」だけ。意味を変える・消すことはしない。

### 5.6 エンジンが使えない間の打鍵

- 預からない。状態が `ready` でない間に届いた要求には、すぐ `{"seq":n,"state":"starting"}`（FAILED 中は
  `"down"`）を返す。TIP は状態を `starting` と知り、その打鍵からアプリへ素通しにする（§7.4）。
- TIP は状態が `ready` でない間、打鍵を送らない（直接入力と同じに素通し）。
- hello に `passes:true` の無い接続（v0.1.2 の DLL。更新の前から開いているアプリに残る）は、準備中も打鍵を送り、
  `state` だけの返事を「食べた」とみなす。この接続には代わりに、エンジンの返事の形で
  `{"seq":n,"pass_through":true,"direct":<その接続の入力モード>}` を返し、打鍵をアプリへ通させる。
  入力モードは、その接続の最後の `set_direct` か、エンジンの返事の `direct` で覚えておく。
- エンジンが終了したら、処理中だった要求に `{"seq":n,"state":…}` を返し、全接続へ `{"event":"reset"}` を送る
  （TIP は見えている文字をそのまま確定する、§7.5）。新しいエンジンが `ready` になったら、
  接続ごとに新しいセッションを開く（かな入力で始まる）。TIP は `ready` を受け取ったとき、直接入力なら
  `set_direct` を送り直す。準備中に切り替えキーを押したときも、TIP は手元の入力モードだけを切り替えて、
  `ready` になってから送る。
- 注意（`lm`）はエンジンごと。エンジンを起動し直したら消し、新しいエンジンが言うものだけを持つ。

### 5.7 試験（CI で実行する）

判断はすべて `broker_core` にあり、偽の土台と時計で試す（`src/broker/tests/broker_core_test.cpp`、どの OS でも）:
起動中の打鍵は `starting` で返る、終了で `reset` と起動し直し、10 分に 3 回で FAILED と通知 1 回、
`retry` で起動、無応答で強制終了。

Windows では本物の `yuragi-broker.exe` を、偽のエンジン（`src/broker/tests/fake_engine.py`。
「N 件目で落ちる」を選べる）と偽の TIP（パイプにつなぐ）で動かす（`tests/test_broker.py`）:

- 3 回落とす → FAILED。`retry` で 1 回だけ起動する。
- ブローカーを強制終了 → エンジンも消える（ジョブ）。2 つ目のブローカーは何もせず終わる。`quit` で両方終わる。
- 本物のエンジンで `--selftest` が通る。

## 6. 変換エンジン（`yuragi/`）

### 6.1 入口: `yuragi/engine.py`

- 標準入力から 1 行 1 JSON を読み、標準出力に 1 行 1 JSON を書く。それ以外の通信手段は持たない。
- 起動直後に、本物の標準出力を通信専用に確保し、`sys.stdout` は標準エラーに向け直す
  （ライブラリが `print` しても通信に混ざらないように）。
- 標準入力が閉じたら（ブローカーが死んだら）終了する。
- ブローカー → エンジン: `{"op":"open","sid":3}` `{"op":"close","sid":3}` `{"sid":3,"seq":17,"op":"down",…}`
- エンジン → ブローカー: 準備ができたら `{"ready":true,"proto":1,"warnings":[…]}`。以後は要求 1 件に返事 1 件
  `{"sid":3,"seq":17,…}`。ready のあとで見つかった注意は `{"event":"warning","warning":"lm"}`（種類ごとに 1 回）。
- セッションは `sid` ごとに 1 つ。辞書・表・学習履歴・個人辞書は全セッションで共有する。
  要求は 1 本のスレッドで順番に処理する。LM は別スレッド（`lm_async.py`、[CONVERSION.md](CONVERSION.md) §9）。
- 1 セッションを標準入出力で直接動かす `python -m yuragi.ime.server` は、試験と評価用。

### 6.2 起動時の読み込み: ファイルごとの方針

原則: **利用者が触れるファイルは、壊れていても起動を止めない。プログラム自身のファイルが壊れていたら、
はっきり止まる。** 黙って飛ばさない。

| ファイル | 壊れていたら | 利用者への知らせ（注意の種類） |
|---|---|---|
| `config.json`（構文・値） | ファイル全体を使わず、すべて既定値 | なし（ログに 1 行） |
| `personal_lexicon.jsonl` の壊れた行 | その行だけ飛ばす | 設定ウィンドウに件数 |
| `learning.jsonl` の壊れた行 | その行だけ飛ばす | 設定ウィンドウに件数 |
| `learning.jsonl` が読めない（他が開いている等） | 学習なしで動く（ファイルが変われば読み直す） | なし（ログに 1 行） |
| 辞書キャッシュが読めない | 消して、辞書から 1 回だけ作り直す（数分） | 起動中の表示（§9.2） |
| 辞書ファイルが無い（中身はインストール時に照合済み。起動時は在るかだけ見る） | **止まる** | あり（停止の通知） |
| LM のモデル・torch が読めない | LM なしで起動（変換はできる） | あり（`lm`） |
| Python のモジュールが読めない | **止まる** | あり（停止の通知） |

辞書キャッシュは、**辞書マニフェストのハッシュを名前にして**、一時ファイルに書いてから置き換える。
「古い辞書のキャッシュを使ってしまう」「書きかけが残る」が、起こりえない。

> **注意**: 辞書の読み込みで、欠けたファイルや読めない行を黙って飛ばさない。辞書の一部（`suffix.txt`）が
> 欠けたまま作られたキャッシュが、変換の質を少し落としたまま気づかれずに使われ続けたことがある。

LM は `local_files_only=True` で読む。**エンジンはネットワークに一切つながない。**

### 6.3 準備完了の前に温める

`ready` を出す前に、ダミーの変換を 1 回実行する（初回 617ms、2 回目以降 9ms）。
利用者の最初の打鍵が遅くならない。

### 6.4 要求 1 件ごとの防壁

エンジンの要求処理ループは、要求 1 件の処理全体を 1 つの `try` で囲む。例外が出たら:

1. `logs\engine.log` に、例外の型と発生箇所（ファイル名・行番号・関数名）を書く。**入力した文字は書かない。**
2. そのセッションを `reset` する。
3. `{"sid":…,"seq":…,"error":true, …リセット後の状態… }` を返す。

エンジンは落ちない。TIP は `error` を見て、見えている文字をそのまま確定する（§7.5）。

これは「握りつぶし」ではない。違いは 3 つ: **記録が残る**、**利用者の文字は残る**、**壊れた状態を捨てて
きれいな状態から続ける**。同じ防壁は 1 か所だけに置き、変換の中身（`session.py` 以下）には置かない。

### 6.5 入力の長さの上限

変換中の入力は `MAX_TOKENS`（200）まで。達したら、文字キーは受け取るが黙って何も変えない。
変換時間は長さに比例する（200 字で 38ms）ので、
これで 1 回の要求の所要時間に上限が付く（I-4）。

### 6.6 止まるときは理由を残す

起動できないと判断したら、標準エラーに `fatal <英数字の短い説明>` を 1 行書いて、終了コード 1 で終わる
（`program-files-unreadable`、`dictionary-missing`、`dictionary-unreadable`、`cache-not-written`）。
ブローカーはこの行と終了コードを `broker.log` に残す。利用者への知らせは原因によらず §9.3 の 1 種類。

### 6.7 学習履歴（`learning.py`）の読み書き

記録の形式と、変換への効き方は [CONVERSION.md](CONVERSION.md) §7。ここではファイルの扱いだけを決める。

1. **自分が書いた分は読み直さない。** 追記したら、同じ行をメモリ上の索引（最新 1 件を持つ辞書）にも足し、
   書いたあとのファイルの大きさと更新時刻を覚える。
2. **他のプログラム（設定ウィンドウ）が書いたら、全体を読み直す。** 変換のたびにファイルの大きさと
   更新時刻を見て、覚えているものと違えば、最初から読み直す。
3. **整理は起動時に 1 回。** 行数が「生きている記録の 2 倍」かつ `COMPACT_MIN_LINES`（5,000）を超えていたら、
   生きている記録だけを一時ファイルに書いて置き換える。
   「生きている」とは: 抑制されておらず、同じ（読み・表記）の中で最新のもの。
4. **読めない・書けないときは**（他が開いている、ディスクの空きが無い等）、ログに 1 行書き、その回は
   学習なしで続ける。変換は止めない。利用者への通知は出さない。
5. 行ごとの検査は、「JSON として読めて、必要な項目がある」だけ。

学習の入／切は `config.json` の `learning`（`on`／`off`。既定 `on`）で決める。
ファイルは最初の確定で作る。

## 7. TIP（`src/tip/yuragi_tip.cpp`）

TSF とのやりとり（キーの受け取り、変換中の文字の描画、表示属性、候補ウィンドウ、言語バー、
トグルキー）と、ブローカーとの接続（`BrokerLink`）。

### 7.1 TIP が持たないもの

エンジンの起動・見張り・再試行、Python の探索と起動、設定ウィンドウの起動は持たない（§2.1。起動してよいのは
ブローカーだけ、§7.3）。通信はパイプだけ。ログは `tip.json` の `log:true` のときだけ書く。

> **注意**: TIP の中で入力を待たない。`ActivateEx` で辞書の準備などを待つと、Windows 11 の
> TextInputHost が止まり、すべての IME が使えなくなる。

### 7.2 接続（`BrokerLink`）

- `Tip` 1 個につき、パイプ 1 本と読み取りスレッド 1 本。
- 読み取りスレッドは、届いた 1 行ごとに解析して、TIP のメッセージ専用ウィンドウへ `PostMessage` する。
  それだけ。ループの中で待つのは「パイプの読み取り」「停止の合図」「接続の合図」の 3 つで、**時間で回るものは無い**。
- 接続を試すきっかけは 3 つだけ: `ActivateEx`、かな入力モードで打鍵があったとき、利用者がメニューで
  「もう一度試す」を選んだとき。前回の試みから `CONNECT_MIN_INTERVAL_MS`（2 秒）以内なら試さない。
- 書き込みは UI スレッドから。重ね合わせ I/O で、`KEY_BUDGET_MS` 以内に書けなければその打鍵は素通し。

### 7.3 ブローカーがいないとき（TIP が起動してよい唯一のもの）

パイプが無かったとき、**次の全部が成り立つ場合に限り**、ブローカーを起動する。

1. `HKCU\Software\yuragi-ime\Tag` が、この DLL のタグ（ビルド時に埋め込む）と同じ。
   ——アンインストール済み・更新済みの古い DLL は、ここで必ず止まる。
2. 保守中の印 `Local\yuragi-ime-maintenance` が無い。——インストーラの作業中は誰も起動しない。
3. このプロセスが、サンドボックスの中でなく、管理者権限でもない（整合性レベルが「中」）。
   ——ブローカーが変な権限で動かないように。条件に合わないプロセスは**接続するだけ**。

回数は数えない。ブローカー自身の二重起動防止（§5.2）と、接続を試す間隔（§7.2 の 2 秒）で足りる。

起動のしかた: 実行ファイルは**この DLL と同じフォルダ**の `yuragi-broker.exe`（`Program Files` の中なので
書き換えられない）。フラグは `CREATE_NO_WINDOW | CREATE_BREAKAWAY_FROM_JOB`、ハンドルは引き継がない、
環境は `CreateEnvironmentBlock` で作ったもの。ジョブからの離脱が許されず起動に失敗したら、その場では
**やり直さない**（次の機会に試す）。

起動したら、パイプが現れるのを最大 `BROKER_WAIT_MS`（10 秒）待つ（100ms 間隔。上限のある待ち）。

通常はサインイン時に Run キーでブローカーが起動しているので、この経路は「ブローカーが何かで消えた」
ときの回復用である。

### 7.4 打鍵の処理（P-1 と I-4 の中心）

次のときは食べず、何も送らない: キーボードが無効、IME が閉じている、フォーカスのある文書が無い、
パスワード欄（§7.7。切り替えキーも食べない）、直接入力、ブローカーにつながっていない、
エンジンが `ready` でない（起動中・停止中。一般的な IME の準備中と同じく素通し。ただし準備中の切り替えキーは
食べて、手元の入力モードを切り替える。§5.6）。
変換中の文字が無いときの Enter・BS・Esc はアプリへ渡す。それ以外は:

1. `OnTestKeyDown`: 手元の状態だけで「食べるか」を答える（通信しない）。
   ただし**返事を待っている要求が 1 件でもあれば、「変換中」とみなして**判定する
   ——待っている文字キーが届けば変換中になるので、後から来た Enter や BS が先にアプリへ抜けるのを防ぐ。
2. `OnKeyDown`: 要求に通し番号 `seq` と打鍵の時刻 `t`（`QueryPerformanceCounter` のミリ秒）を付けて送り、その番号の返事を最大 `KEY_BUDGET_MS`（200ms）待つ。
   - **間に合った** → 同期の編集セッションで画面に反映し、返事に従って食べる／通す。
   - **間に合わなかった** → 1 の判定どおりに食べて、すぐ戻る。**接続は切らない。画面も触らない。**
     返事は後で読み取りスレッドから届く。届いたら非同期の編集セッションで反映する。
3. 返事は必ず `seq` の順に反映する。前の返事がまだなら、届いても待たせる。
4. 返事が `{"seq":n,"state":"starting"}`（または `"down"`）なら、その打鍵はアプリへ通し、以後は状態が
   `ready` に戻るまで送らない。

特別な回復処理は TIP に無い。

### 7.5 「見えている文字をそのまま確定する」

次のどれかを受け取ったら、変換中の文字列があれば**その表示のまま確定して**（文字は消さない。
変換を終了するだけ）、手元の状態を初期化する。

- `{"event":"reset"}`（エンジンが終了した）
- 返事の `"error":true`（その要求で例外が出た）
- 返事・通知の `state` が `down`
- パイプが切れた（ブローカーが消えた）

文字を消してよいのは、利用者が Esc を押したときと、フォーカスが移ってアプリが変換を打ち切ったときだけ。

### 7.6 タイマー

- 常時タイマーは持たない。返事の `timer`（同時打鍵の判定期限、LM 待ちの次の問い合わせ時刻）があるときだけ、
  その時刻に 1 回鳴るタイマーを掛ける。鳴ったら `timeout` を送る。
- 候補ウィンドウの位置は、TSF の配置変更通知（`ITfTextLayoutSink::OnLayoutChange`）で直す。
- トグルキーを離したことの確認（予約キーは離した通知が来ないことがある）は、次の打鍵のときに
  `GetKeyState` で見る。

### 7.7 パスワード欄

入力欄の種類（`IS_PASSWORD`・`IS_NUMERIC_PASSWORD` ならパスワード欄）は、**フォーカスが移ったときに 1 回**調べて覚える（読み取り専用の編集セッション）。
同期で調べられなければ非同期で頼み、答えが出るまでは「調べ中」として素通しにする。
「選択範囲が取れない」「入力欄の種類が取れない」は、パスワード欄の証拠として扱わない。
打鍵ごとの問い合わせはしない。

### 7.8 試験

TIP 本体は TSF の中でしか動かないが、**判断の部分は切り出して普通の試験にする**。

- 「返事の解釈」「食べるかどうかの判定」「seq の順序付け」「状態から表示への対応」を、TSF に依存しない
  ヘッダ（`src/tip/tip_logic.h`）に置き、`tip_logic_test` で試験する（どの OS でも動く）。
- 全体は §10.6 の実地試験で確かめる。

## 8. インストール・更新・アンインストール

利用者と開発者向けの手順の説明は [INSTALL.md](INSTALL.md)。

### 8.1 共通の仕組み

- **保守中の印**: `setup.ps1` と `uninstall.ps1` は、最初に（管理者権限でない側で）ミューテックス
  `Local\yuragi-ime-maintenance` を作って持つ。スクリプトが終われば、成功でも失敗でも強制終了でも、
  Windows が自動で消す。**消し忘れが起こりえない。** この印がある間、TIP はブローカーを起動しない
  （動いているブローカーには、スクリプトが `quit` を送る）。
- **管理者権限で行うのは 3 つだけ**（UAC は 1 回）: ①`Program Files` へのファイルの配置、
  ②`regsvr32` による登録／解除、③古い版の `Program Files` 側の削除。
  これは小さな PowerShell スクリプト（`packaging/elevated.ps1`）にまとめ、**Python は管理者権限で動かさない。**
  呼び出しは `-EncodedCommand`（スクリプトのパスと引数を 1 つのコマンドにして符号化する。空白・引用符・
  日本語を含むパスも崩れない）。結果は終了コードと、利用者側が読める結果ファイルで返す。
- **登録の確認**: 登録／解除のあと、`elevated.ps1` がレジストリを読み返して確かめる（1 か所だけ）。
  確かめられなければ失敗として扱う（I-6）。
- **使用中のファイル**: 消せないファイル（アプリが読み込んでいる DLL）はそのまま残し、次の実行で消す。
  版ごとのフォルダなので、残っても邪魔にならない。
  `DllUnregisterServer` は、どれか 1 つでも失敗したら失敗を返す。
  > **注意**: 登録解除は、カテゴリ → プロファイルの順に消す。プロファイルを先に消すと TIP のキーが
  > カテゴリごと消え、後のカテゴリ解除が E_FAIL を返して、全部消えているのに登録解除が失敗と報告される。
- **言語一覧への追加・削除**（`InstallLayoutOrTip`）は利用者ごとの設定なので、管理者権限でない側で行う
  （別の管理者アカウントで昇格したとき、その管理者の設定を変えてしまわないように）。
- 事前の接続確認、Python の探索、照合なしの分岐は持たない。

### 8.2 インストールと更新（同じ手順）

| 段 | すること | ここで失敗したら |
|---|---|---|
| 1 | 保守中の印を立てる | — |
| 2 | `staging\<tag>\` に取得・照合・展開。足りない共有物（ランタイム・辞書・モデル）だけ `shared\` に作る。共有物は「作りかけの名前で作って、完成したら改名」。ランタイムは Python の埋め込み版に、リリースに添えた同じ版の tkinter 一式（`python-<版>-tkinter-amd64.zip`）を重ね、torch・依存とあわせて読み込めることを確かめる | 何も変わっていない。旧版が動き続ける。やり直せば続きから |
| 3 | **本物のブローカーで試運転**: `yuragi-broker.exe --selftest <staging の engine.json>`。エンジンを実際に起動し、変換を 1 回行って終了コードを返す | 同上 |
| 4 | `staging\<tag>` を `versions\<tag>` へ改名（一瞬）。`versions\<tag>` が既にあれば脇へ寄せる。それが入っている版（Tag が同じ）なら同じ版の入れ直しで、先にそのブローカーを止める。違えば前回の途中の残りで、動いている版には触らない | 同上 |
| 5 | 管理者権限: `Program Files\yuragi-ime\<tag>\` に配置、登録を新しい DLL に付け替え、読み返して確認 | 旧版の登録のまま。旧版が動き続ける |
| 6 | 旧ブローカーに `quit`。`HKCU\…\Tag` と Run キーを新しい版に書き換え、言語一覧に追加 | — |
| 7 | 印を下ろし、新ブローカーを起動して `ready` を待って確認（最大 60 秒） | 理由を表示。次のサインインでも起動を試みる |
| 8 | 旧版の片付け: `versions\` と `shared\` の使われていないもの。`Program Files` 側の旧版は 5 の管理者権限の中で消す（使用中のものは残す） | 片付けの失敗はインストールの失敗にしない。次回の setup がまた試す |

- 4 までは、動いている版に一切触らない。5〜7 は数秒。
- 更新のあと、開いたままのアプリには旧 DLL が残る。旧 DLL は §7.3 の条件 1 により何も起動せず、
  新ブローカーに接続する（プロトコル 1 のまま項目を足すだけなので、そのまま動く）。
- 初回の途中失敗: `staging\` は自分の作業場なので、いつでも消して作り直してよい。

> **注意**: Python の埋め込み版には tkinter が無い。ランタイムの作り方を変えるときは、設定ウィンドウが
> 開くこと（`import tkinter; tkinter.Tcl()`）まで確かめる。インストールと変換が通っても、これは見つからない。

### 8.3 アンインストール

1. 保守中の印（この間 TIP はブローカーを起動しない）。
2. Run キーを消し、言語一覧から外す。
3. ブローカーに `quit`（エンジンも終了する）。
4. 管理者権限: 登録解除、読み返して確認。`Program Files\yuragi-ime\` を削除。使用中のファイルは残す（§8.1）。
5. HKCU の `Software\yuragi-ime`（Tag）と、言語一覧から外したときに Windows が書く
   TSF の利用者設定（`SOFTWARE\Microsoft\CTF\TIP\{CLSID}`）を削除。`%LOCALAPPDATA%\yuragi-ime\` を削除。
   Tag は登録解除のあとで消すので、途中で止まっても、入口（Tag で版を見つける）からやり直せる。
6. 結果を表示する。使用中のファイルが残ったときは「登録は外れているので使われません。アプリを閉じたあとに
   削除できます」と伝える。**サインアウトや再起動を求めない。**

`~\.yuragi-ime\`（学習履歴・個人辞書・設定）は**残す**。消すのは `-RemoveData` を付けたときだけで、
そのときも消す前に場所と大きさを表示する（I-7）。

### 8.4 開発時（`dev-build.ps1`・`dev-register.ps1`）

- ビルドと登録を分ける: `dev-build.ps1`（ビルドとテストだけ。CI もこれ）と `dev-register.ps1`（登録）。
- 開発用のタグは `dev`。`HKCU\…\Tag = dev`、`versions\dev\engine.json` はリポジトリを指す。
  DLL とブローカーは `dist\` から読み込む（開発機に限り `Program Files` 配置を省く）。
- リリースビルドは `-DCMAKE_BUILD_TYPE=Release` を明示する。

## 9. 利用者に見えるもの

原則: **普通の利用者は、「ゆ」と「Y」以外のものを見ない。** 見せるのは、利用者が何かしないと
直らないときだけ。見せるときは、何が起きたか・文字は無事か・どうすればよいか、を 1 つの文で言う。
どれも**フォーカスを取らず、クリックしなくても消える。** 利用者向けの説明は [USAGE.md](USAGE.md)。

### 9.1 状態は 4 つ

| 状態 | タスクバー | 打鍵 | いつ |
|---|---|---|---|
| 通常 | 「ゆ」／「Y」 | 変換される | ほぼ常に |
| 準備中 | 「ゆ」／「Y」（薄く） | そのまま通る（直接入力と同じ）。切り替えキーは効く | サインイン直後の数秒、エンジンの起動し直し中 |
| 停止 | 「!」 | そのまま通る | 自動で直せなかったとき |
| 対象外 | 「Y」 | そのまま通る | 更新作業中、この利用者には未インストール、サンドボックス・管理者のアプリでブローカーが無い |

### 9.2 カーソルの近くに出す小さな表示

候補ウィンドウと同じ作り（`WS_EX_NOACTIVATE`。フォーカスを取らない・クリックを取らない）で、
文字入力位置の下に 1 行だけ出す。

出すのは 1 種類だけ。

| いつ | 文言 | 消える条件 |
|---|---|---|
| 停止中に、かな入力のつもりで文字キーを押した（フォーカスごとに 1 回） | `日本語変換が止まっています。タスクバーの「!」を右クリックしてください` | 4 秒 |

> **注意**: 文字位置の矩形が「幅 0・高さあり」（キャレット）で返るのは普通である。
> 見えていない判定は「高さが無い」だけにする。`IsRectEmpty` で判定すると、Notepad では候補窓が毎回隠れる。

### 9.3 通知（ブローカーが出す。停止に入ったときに 1 回だけ）

Windows の通知（`Shell_NotifyIcon` の通知。フォーカスを取らない）で、1 種類だけ:

> **ゆらぎ: 日本語変換が止まりました**
> 入力済みの文字はそのまま残っています。ここを押すと、もう一度試せます。

押すと、ブローカーが小さな案内（ネイティブのダイアログ `TaskDialogIndirect`。Python に頼らない——Python が
壊れているときにも出せるように）を開く。これは利用者が押して開くものなので、ウィンドウを出してよい。
本文は「変換エンジンが繰り返し止まったか、反応しなくなりました。「もう一度試す」で起動し直します。
直らなければ、インストールの1行をもう一度実行してください。」、ボタンは `もう一度試す`
`記録のフォルダを開く` `閉じる`。原因（終了コード、`fatal` 行）は `broker.log` に残す。

起動はできている軽い異常（LM が使えない）は通知しない。
`broker.log` に残し、設定ウィンドウの「状態」タブに「注意」として出す。

止まったことは `logs\notices.log` にも残す（設定ウィンドウの「最後に止まった理由」）。

### 9.4 タスクバーのメニュー（右クリック）

| 状態 | 項目 |
|---|---|
| 通常 | `直接入力に切り替え`／`かな入力に切り替え`、`設定を開く` |
| 準備中 | `（変換の準備をしています）`（押せない）、`設定を開く` |
| 停止 | `もう一度試す`、`設定を開く` |

設定ウィンドウは TIP が起動するのではなく、ブローカーに `open_admin` を頼む（ブローカーが `pythonw.exe` で起動）。
設定ウィンドウの「状態」タブに、ブローカーとエンジンの状態・注意・最後に止まった理由・学習履歴の行数を出す。
設定を変えたあとの「変換エンジンを再起動」は、ブローカーへの `retry` と同じ仕組みで行う。

## 10. 試験と合格条件

部品ごとの合格条件。番号付きの段（第 1 段など）は、コードのコメントが参照している呼び名。

### 10.1 エンジン（第 1 段。Python の単体試験）

- 変換結果は変わらない（変換の試験がすべて通る）。
- 壊れた `config.json` は既定値で、壊れた個人辞書の行は飛ばして、`ready` に達する。
- 辞書ファイルを 1 つ消すと `fatal dictionary-missing` で止まる。
- 学習: 確定した変換が次から先頭に出る。Shift+F6 と設定ウィンドウの「忘れる」が、動いているセッションに効く。
- 要求の処理中に例外を起こすテスト用の口から、`error:true` が返り、次の要求は正常。
- 201 字目は何も変えない。
- エンジンのプロセスが、起動から終了までネットワーク接続を 1 本も開かない。
- 全 TIP 接続のセッションを 1 つのエンジンで扱い、辞書などを共有する（`tests/test_engine_sessions.py`）。

### 10.2 ブローカー（第 2 段）

- §5.7 の全項目が CI で通る（本物のエンジンでの `--selftest` を含む）。

### 10.3 TIP（第 3 段）

- `tip_logic.h` の単体試験（返事の解釈、食べる判定、順序、状態と表示）。
- 実地試験（§10.6）の 1〜5, 11, 13。

### 10.4 インストーラ（第 4 段）

- 実地試験の 6〜10, 12。CI の install-test とリリースの検証（`.github/workflows/release.yml`）は、
  まっさらな Windows ランナーで入れて消す。

### 10.5 全体（第 5 段）

- 実地試験の全項目を、まっさらな Windows で通しで 1 回。その記録（プロセスとウィンドウの一覧）を残す。

### 10.6 実地試験（Windows サンドボックスか仮想マシン）

各操作の間、**新しく生まれたプロセスと新しく現れた最上位ウィンドウを記録する**。
メモ帳・ブラウザ・エクスプローラを開き、IME を選んで打鍵した状態から始める。

| # | 操作 | 期待 |
|---|---|---|
| 1 | インストール → IME を選ぶ → かなを打って変換 | 変換できる。常駐はブローカー 1・エンジン 1。ウィンドウ 0 |
| 2 | 変換の途中でエンジンをタスクマネージャーで終了し、打ち続ける | 見えていた文字が残る。起動し直す間の打鍵はそのまま（英字で）入り、数秒後から変換される。ウィンドウ 0 |
| 3 | エンジンを 10 分以内に 3 回終了 | 3 回目で「!」と通知 1 回。以後、起動 0 回 |
| 4 | メニューの「もう一度試す」 | 戻る |
| 5 | ブローカーをタスクマネージャーで終了し、打鍵する | 数秒で戻る |
| 6 | `config.json` を壊してサインインし直す | 変換できる（既定の設定で） |
| 7 | 辞書ファイルを 1 つ消してサインインし直す | 「!」と通知 1 回。起動はちょうど 3 回 |
| 8 | **アプリを開いたまま**更新 | 終わる。開いていたアプリでそのまま打てる。学習が残る |
| 9 | 更新の途中（取得中）で回線を切る／setup を強制終了 | 旧版で打てる。やり直すと終わる |
| 10 | **アプリを開いたまま**アンインストール | 終わる。60 秒、プロセス 0・ウィンドウ 0。学習履歴は残っている |
| 11 | スタートメニューの検索欄、「設定」、管理者として開いたメモ帳で打鍵 | 変換できる、または黙って素通し。どちらでもプロセスの起動 0 |
| 12 | 初回インストールの途中で回線を切る → やり直す | 手で何も消さずに終わる |
| 13 | 再起動してサインイン直後に打鍵 | 準備中（薄い「ゆ」）の間はそのまま入り、準備ができたら変換される |

## 12. やらないこと（理由つき）

| 項目 | 理由と、やる場合の方向 |
|---|---|
| **辞書のメモリ（1,260MB）と読み込み時間（2.35 秒）の削減** | この設計で残る最大の弱点。メモリが足りない PC では、エンジンが OS に止められやすい。辞書を Python のオブジェクトとして持つのをやめ、ファイルを直接参照できる形式にすれば、メモリも起動時間も 1 桁下がる見込み。変換の中身に触るので、構造とは分けて行う |
| LM を別プロセスに分ける | torch が原因でエンジンごと落ちる事例が `engine.log` に出たら行う。分け方は「候補の生成はエンジン、点数付けだけ LM プロセス」 |
| 32 ビットアプリ、ARM 版 Windows | 配置と通信は対応できる形にしてある（パイプはビット数に依らない）。DLL を追加でビルドすれば足りる。いまは setup が ARM を「まだ対応していません」と表示して止まる |
| 打鍵の記録・再生による変換状態の完全復元 | §2.3。状態が増える割に、得るものが小さい |
| 自動更新 | 利用者が頼んでいないときに何かを取りに行かない |

## 13. Windows の挙動に依る前提

次は Windows の挙動に頼っている。前提が崩れたときの動きも決めてある。

- パイプのアクセス権: サンドボックス内のアプリ（スタートメニューの検索欄）から接続できる設定（§5.5）。
  接続できない場合、そこでは「対象外」として素通しになる（何も起動しないことは §7.3 で保証済み）。
- `CREATE_BREAKAWAY_FROM_JOB` が拒否される環境では、TIP はブローカーを起動しない（§7.3）。
- `Shell_NotifyIcon` の通知が、全画面アプリの上でフォーカスを取らないこと。
- 候補ウィンドウの位置直しを配置変更通知に頼ること（通知を出さないアプリでは、候補窓の位置が古いままになる）。
